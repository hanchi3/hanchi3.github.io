用户认证

HTTP是一个无状态的协议，每次客户端和服务器之间的交互都是相互独立的，服务器在处理请求时不会存储关于客户端的任何信息。一次请求结束后，下次在发送服务器就不知道这个请求是谁发来的了(同一个IP不代表同一个用户)，在Web应用中，用户的认证和鉴权是非常重要的一环。

Cookie-Session 认证模式

Cookie–小型文本文件

Cookie 是一种由服务器生成并通过 HTTP 响应头发送到客户端的文本信息，保存在浏览器中，用于存储客户端的信息、状态、偏好设置等。
当用户后续向同一网站发起请求时，浏览器会自动将相关的 Cookie（通常是与该域名匹配的 Cookie）附加到请求中发送给服务器。
Cookie 是实现 会话管理 和 状态保持 的常用工具。

Session–服务端机制

在 Session 机制中，服务器为每个用户生成一个 Session ID（会话标识符），这个 ID 用于标识该用户的会话信息。
这个 Session ID 会被存储在浏览器的 Cookie 中（例如 Set-Cookie: sessionid=abc123）。

基于 Cookie-Session 的会话管理方式

用户登录时，客户端使用用户名、密码进行认证。
服务端验证用户名、密码正确后生成并存储Session（保存与用户相关的状态数据，如用户ID、角色等），将SessionID通过Cookie返回给客户端。
客户端将SessionID存储在浏览器的Cookie中，访问需要认证的接口时在Cookie 中携带SessionlD发给服务器。
服务端通过SessionID查找Session并进行鉴权，返回给客户端需要的数据。

优缺点

优点：

  • 1.简单易用：对于单体应用，使用 Cookie-Session 认证非常简单，配置容易。
  • 2.无状态性：服务器不需要保存用户的认证信息，只需保存 Session ID。

缺点：

  • 1.可扩展性差：Session 数据通常保存在服务器端，内存或内存数据库中，随着并发量的增加，可能会成为性能瓶颈。
  • 2.跨域问题：由于 Cookie 有跨域限制，在分布式系统或微服务架构中，需要处理跨域问题，将所有Session单独存储并共享。

JWT认证模式

JWT– JSON Web Token

一种基于 JSON 格式的开放标准，用于在网络应用环境中传递声明（Claims）。
JWT 由三部分组成，每一部分之间用 “.” 进行分隔,一个JWT Token 就像这样:

  • 1.Header（头部）：包含元数据，用来描述令牌的类型和签名算法。

头部被 Base64Url 编码后形成第一部分。

  • 2.Payload（负载）：包含声明（claims），即传递的数据，如用户 ID、过期时间等。负载部分是可解码的，但未经加密的，不能完全信任。

  • 3.Signature（签名）：用于确保 JWT 的数据未被篡改，并验证发送方的身份。签名部分是通过指定的算法对前两部分进行加密生成的。
    签名的生成方法是：

    用密钥（对于对称算法是共享的密钥，非对称算法是私钥）进行加密。

基于 Token 的无状态会话管理方式

用户登录：
用户通过用户名和密码登录。
服务器验证用户身份后，生成一个 JWT，其中包含用户信息和声明（如用户 ID、过期时间等）。
服务器使用私钥对 JWT 进行签名，然后将其发送到客户端。

客户端存储 JWT：
客户端（通常是浏览器或移动端）接收到 JWT 后，会将其保存在本地（如 localStorage 或 sessionStorage）或内存中。

用户请求受保护资源：
用户发起对受保护资源的请求时，客户端将 JWT 附加到 HTTP 请求的 Authorization 头部（通常是 Bearer 认证模式）。
Authorization: Bearer

服务器验证 JWT：
服务器收到请求后，会从请求头中提取 JWT，并验证其签名（使用公钥或共享密钥验证）。
如果 JWT 验证通过，且未过期，服务器会允许访问受保护的资源。
如果验证失败或 JWT 已过期，服务器会拒绝请求，返回相应的错误信息。

优缺点

优点

  • 1.无状态：
    JWT 是一种 无状态 认证机制，服务器无需存储用户会话信息。所有的认证数据都包含在 JWT 本身中，因此每个请求都是自包含的，服务器只需验证签名和有效性即可。
  • 2.灵活的声明：
    由于 JWT 可以包含任意的声明信息，开发者可以根据需要将任意数据嵌入到 JWT 中，这使得 JWT 特别适合传递用户信息、权限数据等。

带有 Refresh Token 机制的 JWT 认证

解决了 JWT 本身的一些限制（如过期管理）。在没有 Refresh Token 的情况下，JWT 的有效期通常是固定的，一旦过期，用户需要重新登录，而引入 Refresh Token 后，可以有效地延长用户的登录状态，避免频繁登录，同时保持系统的安全性。

两个token

在带有 Refresh Token 机制的 JWT 认证流程中，通常会使用两个不同的 token：
Access Token（访问令牌）：包含用户的认证信息和授权数据，通常有效期较短（如 15 分钟）。
Refresh Token（刷新令牌）：用于获取新的 Access Token，有效期较长（如几天、几周或几个月）。

  • 生成时：在调用 GenToken 函数时，生成了一对 token。
  • 刷新时：当 access_token 过期时，传入有效的refresh_token和过期的access token，生成了一对新 token。

工作流程步骤

用户登录：

用户通过用户名和密码进行身份验证。
服务器验证成功后，生成一个 Access Token 和一个 Refresh Token。
Access Token 立即返回给客户端，通常存储在浏览器的 localStorage 或 sessionStorage 中。
Refresh Token 也一并返回，但它一般存储在服务器端或者客户端的 httpOnly Cookie 中，以确保它不容易受到跨站脚本攻击（XSS）的威胁。

客户端发起请求：
用户进行后续请求时，客户端会将 Access Token 附加到请求的 Authorization 头部中：
Authorization: Bearer

服务端验证有效性：
服务器验证 Access Token 的有效性。如果 Access Token 仍然有效，服务器返回请求的资源。如果 Access Token 已过期，服务器会返回一个 401 Unauthorized 响应，告知客户端重新认证。

Access Token 过期：
当响应返回 401 Unauthorized 错误时，客户端会向服务器发送包含 POST /refresh-token 的请求。Refresh Token 的作用是向服务器证明用户身份。

服务器验证 Refresh Token：
如果Refresh Token没有过期，服务端向客户端下发新的Access Token 和 Refresh Token。
只要用户持续活跃，每次刷新 Access Token 时，都会顺带刷新 Refresh Token，因此 Refresh Token 的有效期可以被“重置”。这意味着，只要用户继续访问， Refresh Token 的有效期会不断延长。如果 Refresh Token 的有效期到期（例如 7 天），且用户未访问，则 Refresh Token 过期，用户需要重新登录才能获取新的 Access Token 和 Refresh Token。
如果 Refresh Token 无效或已过期，服务器会返回 401 Unauthorized 或 400 Bad Request，要求客户端重新登录。

客户端使用新 Access Token：
客户端接收到新的 Access Token 后，可以继续在后续请求中使用新的 Access Token，直到它再次过期。

**后端需要对外提供一个刷新Token的接口，前端需要实现一个当Access Token过期时自动请求刷新Token接口获取新Access Token的拦载器。**

优缺点

优点：

  • 1.延长登录有效期：通过 Refresh Token，用户可以在不需要频繁登录的情况下，保持长时间的认证状态，同时避免 Access Token 泄露带来的安全隐患。
  • 2.更好的安全性：将 Refresh Token 存储在安全位置（如 httpOnly Cookie 中），可以减少 XSS 攻击的风险；并且 Refresh Token 的有效期较长，可以防止频繁的登录过程。
  • 3.灵活的权限控制：如果 Refresh Token 被盗，服务器可以撤销其有效性，阻止攻击者伪造 Access Token。
    缺点：
    额外的请求：每当 Access Token 过期时，客户端需要发送额外的请求来获取新的 Access Token，这会增加一定的网络开销。
