map 的数据结构

什么是map

由一组 <key, value> 对组成的抽象数据结构，并且同一个 key 只会出现一次。

map 作为一种 抽象数据结构，主要是为了在键值对存储中提供高效的查找、插入和删除操作。实际上，map 可以通过多种不同的数据结构来实现，具体选择哪种实现方式，取决于应用场景的需求。以下是几种常见的 map 实现结构：

  • 哈希表（Hash Table）
    哈希表是最常见的 map 实现方式，它通过一个哈希函数将 key 映射到不同的桶（bucket，也就是数组的不同 index）。哈希表的主要优势是查找、插入和删除操作通常能够在 O(1) 的平均时间复杂度下完成（哈希冲突不严重的情况下）。
    哈希查找表一般会存在“碰撞”的问题，就是说不同的 key 被哈希到了同一个 bucket。一般有两种应对方法：链表法和开放地址法。链表法将一个 bucket 实现成一个链表，落在同一个 bucket 中的 key 都会插入这个链表。开放地址法则是碰撞发生后，通过一定的规律，在数组的后面挑选“空位”，用来放置新的 key。

  • 搜索树
    搜索树法一般采用自平衡搜索树，包括：AVL 树，红黑树。一种自平衡的二叉查找树，它确保树的高度在 O(log n) 范围内，从而提供查找、插入和删除操作的 O(log n) 时间复杂度。遍历自平衡搜索树，返回的 key 序列，一般会按照从小到大的顺序；而哈希查找表则是乱序的。

前面说了 map 实现的几种方案，Go 语言采用的是哈希查找表，并且使用链表解决哈希冲突。

go 中解决哈希冲突

链地址法

当有两个或以上数量的键被哈希到了同一个bucket时，我们称这些键发生了冲突。Go使用链地址法来解决键冲突。

由于每个bucket可以存放8个键值对，所以同一个bucket存放超过8个键值对时就会再创建一个键值对，用类似链表的方式将bucket连接起来。

bucket数据结构指示下一个bucket的指针称为overflow bucket，意为当前bucket盛不下而溢出的部分。事实上哈希冲突并不是好事情，它降低了存取效率，好的哈希算法可以保证哈希值的随机性，但冲突过多也是要控制的，后面会再详细介绍。

例如，对于一个bucket数量为4，包含4个键值对的哈希表来说，这个哈希表的负载因子为1。哈希表需要将负载因子控制在合适的大小，超过其阀值需要进行rehash，也即键值对重新组织：

  • 哈希因子过小，说明空间利用率低
  • 哈希因子过大，说明冲突严重，存取效率低
    每个哈希表的实现对负载因子容忍程度不同，比如Redis实现中负载因子大于1时就会触发rehash，而Go则在在负载因子达到6.5时才会触发rehash，因为Redis的每个bucket只能存1个键值对，而Go的bucket可能存8个键值对，所以Go可以容忍更高的负载因子。

其他解决哈希冲突办法

  • 开放定址法：我们在遇到哈希冲突时，去寻找一个新的空闲的哈希地址。
  • 再哈希法：同时构造多个不同的哈希函数，等发生哈希冲突时就使用第二个、第三个……
  • 建立公共溢出区：将哈希表分为基本表和溢出表，将发生冲突的都存放在溢出表中。

扩容

触发 map 扩容的条件

为了保证访问效率，当新元素将要添加进map时，都会检查是否需要扩容，扩容实际上是以空间换时间的手段。
触发扩容的条件有二个：

  • 负载因子 > 6.5时，也即平均每个bucket存储的键值对达到6.5个。为什么这么做很容易理解
  • overflow 的 bucket 数量过多时。当 B < 15 时：如果溢出桶的数量超过当前桶总数，则触发扩容。当 B >= 15 时：如果溢出桶的数量超过 2^15，即 noverflow >= 32768，则触发扩容。

增量扩容

当负载因子过大时，就将 B 加 1，bucket 最大数量2^B直接变成原来 bucket 数量的 2 倍。然后旧 bucket 数据搬迁到新的 bucket。

由于 map 扩容需要将原有的 key/value 重新搬迁到新的内存地址，如果有大量的 key/value 需要搬迁，会非常影响性能。故Go采用逐步搬迁策略，即每次访问map时都会触发一次搬迁，每次搬迁2个键值对。

之前map存储了7个键值对，只有1个bucket。此地负载因子为7。再次插入数据时将会触发扩容操作，扩容之后再将新插入键写入新的bucket。

等量扩容

所谓等量扩容，实际上并不是扩大容量，buckets数量不变，重新做一遍类似增量扩容的搬迁动作，把松散的键值对重新排列一次，以使bucket的使用率更高，进而保证更快的存取。
开辟一个新 bucket 空间，将老 bucket 中的元素移动到新 bucket，使得同一个 bucket 中的 key 排列地更紧密。原因：有这样一种情况，先插入很多元素，导致创建了很多 bucket，之后，删除元素降低元素总数量，导致创建很多的 overflow bucket，但就是不会触犯第 1 点的规定。overflow bucket 数量太多，导致 key 会很分散，查找插入效率低得吓人，因此出台第 2 点规定。这就像是一座空城，房子很多，但是住户很少，都分散了，找起人来很困难。

查找过程

key 经过哈希计算后得到哈希值，共 64 个 bit 位（64位机），计算它到底要落在哪个桶时，只会用到最后 B 个 bit 位。（B个bit位就可唯一确定2^B个bucket）。

  1. **根据key值算出哈希值。**例如，现在有一个 key 经过哈希函数计算后，得到的哈希结果是：

B = 5，那么桶的数量，也就是 buckets 数组的长度是 2^5 = 32。
2. **取哈希值低位与hmap.B取模确定bucket位置。**用最后的 5 个 bit 位，也就是 01010，值为 10，也就是 10 号桶。
3. 取哈希值高位在tophash数组中查询，遍历 bucket 中的 key。
4. 如果tophash[i]中存储值也哈希值相等，则去找到该bucket中的key值进行比较，找到了。
5. 如果在 bucket 中遍历完还没找到，并且 overflow 不为空，还要继续去 overflow bucket 中寻找，直到找到或是所有的 key 槽位都找遍了，包括所有的 overflow bucket。
6. 如果当前处于搬迁过程，则优先从oldbuckets查找
如果访问 map 中不存在的键，则返回该值类型的零值。例如，对于 map[string]int，若键不存在，则返回 0。

插入过程

新元素插入过程如下：

  1. 根据key值算出哈希值
  2. 取哈希值低位与hmap.B取模确定bucket位置
  3. 查找该key是否已经存在，如果存在则直接更新值
  4. 如果没找到将key，将key插入
