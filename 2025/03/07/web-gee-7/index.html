panic 和 recover

在 Go 语言中，panic 和 recover 主要用于处理异常情况。

panic - 触发运行时错误

panic 用于立即终止程序的执行，并向上层函数传播错误，直到 recover 捕获它，或者程序崩溃。通常用于严重错误，如数组越界、除零、空指针访问等。
注意： panic 之后的代码不会执行，程序会直接崩溃。

recover - 捕获 panic 并恢复

recover 用于拦截 panic，防止程序崩溃。但 recover 只能在 defer 语句中生效，如果不在 defer 里调用，recover 不会生效。

注意事项

  • recover 只能在 defer 中使用，如果 recover 不在 defer 里调用，它不会捕获 panic。
  • 不应该滥用 panic，panic 适用于可恢复的错误（如 nil 指针访问）。一般错误（如用户输入错误）应该使用 error 机制，而不是 panic。
  • recover 只能恢复 panic，但不能恢复 goroutine。recover 只能捕获同一 goroutine 的 panic，不能拦截其他 goroutine 的 panic。

Gee 的错误处理机制

为什么需要错误处理机制

对一个 Web 框架而言，错误处理机制是非常必要的。可能是框架本身没有完备的测试，导致在某些情况下出现空指针异常等情况。也有可能用户不正确的参数，触发了某些异常，例如数组越界，空指针等。如果因为这些原因导致系统宕机，必然是不可接受的。

Recovery 中间件

在 Web 框架 gee 中，我们希望在发生 panic 时能够捕获错误，并记录详细的调用堆栈信息，而不是让整个服务器崩溃。Recovery 中间件 正是用于拦截 panic 并优雅地处理错误的。

我们将在 gee 中添加一个非常简单的错误处理机制，即在此类错误发生时，向用户返回 Internal Server Error，并且在日志中打印必要的错误信息，方便进行错误定位。

将错误处理作为一个中间件，新增文件 gee/recovery.go，在这个文件中实现中间件 Recovery。

Recovery 的实现非常简单，使用 defer 挂载上错误恢复的函数，在这个函数中调用 recover()，捕获 panic，并且将堆栈信息打印在日志中，向用户返回 Internal Server Error。这里有一个 trace() 函数，这个函数是用来获取触发 panic 的堆栈信息。

在 trace() 中，调用了 runtime.Callers(3, pcs[:])，Callers 用来返回调用栈的程序计数器, 第 0 个 Caller 是 Callers 本身，第 1 个是上一层 trace，第 2 个是再上一层的 defer func。因此，为了日志简洁一点，我们跳过了前 3 个 Caller。
