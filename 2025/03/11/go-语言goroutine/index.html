为什么需要调度器？

定义

  • 进程：是应用程序的启动实例，每个进程都有独立的内存空间，不同的进程通过进程间的通信方式来通信。
  • 线程：从属于进程，每个进程至少包含一个线程，线程是 CPU 调度的基本单位，多个线程之间可以共享进程的资源并通过共享内存等线程间的通信方式来通信。
  • 协程：为轻量级线程，与线程相比，协程不受操作系统的调度，协程的调度器由用户应用程序提供，协程调度器按照调度策略把协程调度到线程中运行。

计算机并发的发展

早期的单进程操作系统，面临2个问题：

  1. 单一的执行流程，计算机只能一个任务一个任务处理。
  2. 进程阻塞所带来的CPU时间浪费。

多进程/多线程时代（引入调度器）：
后来操作系统就具有了最早的并发能力：多进程并发，通过进程/线程切换，当一个任务阻塞时，CPU 可以执行其他任务，提高利用率。问题：

  1. 进程占用资源多，进程创建、销毁、调度、切换开销大（涉及内存、页表、文件句柄等）。导致 CPU 资源被浪费在进程管理上，而不是用于执行实际计算任务。
  2. 线程虽然比进程轻量，但涉及同步竞争（锁、资源争抢），增加编程复杂度。

协程时代（用户态线程）：
协程是一种在用户态运行的轻量级线程，可以在单个或多个线程上调度多个任务。特点：

  1. 协程切换无需陷入内核态，发生在用户态，只需保存/恢复少量寄存器，不涉及内核调度，切换速度极快。避免频繁的线程/进程切换，减少内核态开销，提高 CPU 利用率。
  2. 协程本质上是一个函数执行过程，由运行时管理，创建和销毁开销极小。
  3. 协程是单线程内调度的，多个协程在同一个线程内按顺序执行，避免了并发竞争，因此不需要加锁，避免了线程同步锁的开销。
  4. 线程调度是抢占式的，内核会定期打断线程并强行调度其他线程执行。协程调度是协作式的，只有协程主动让出执行权时，才会切换到下一个协程，避免了不必要的上下文切换。

3种协程和线程的映射关系

N:1 关系

N个协程绑定1个线程，优点就是协程在用户态线程即完成切换，不会陷入到内核态，这种切换非常的轻量快速。缺点：某个程序用不了硬件的多核加速能力。一旦某协程阻塞，造成线程阻塞，本进程的其他协程都无法执行了，根本就没有并发的能力了。

1:1 关系

1个协程绑定1个线程，这种最容易实现。协程的调度都由CPU完成了，不存在N:1缺点。协程的创建、删除和切换的代价都由CPU完成，有点略显昂贵了。与不使用协程一样了。

Go语言的协程 goroutine

M:N 模型

Golang 采用的是 M:N 调度模型（多个 Goroutine 运行在多个 OS 线程上）。
让一组可复用的函数运行在一组线程之上，即使有协程阻塞，该线程的其他协程也可以被runtime调度，转移到其他可运行的线程上。最关键的是，程序员看不到这些底层的细节，这就降低了编程的难度，提供了更容易的并发。

Go中，协程被称为goroutine，它非常轻量，一个goroutine只占几KB，并且这几KB就足够goroutine运行完，这就能在有限的内存空间内支持大量goroutine，支持了更多的并发。虽然一个goroutine的栈只占几KB，但实际是可伸缩的，如果需要更多内容，runtime会自动为goroutine分配。

GMP 模型

模型布局

调度器中，除了 M(thread) 和 G(goroutine)，又引进了 P(Processor)。
Processor，它包含了运行goroutine的资源，如果线程想运行goroutine，必须先获取P，P中还包含了可运行的G队列。
在 GPM 模型，有一个全局队列（Global Queue）：存放等待运行的 G，还有一个 P 的本地队列：也是存放等待运行的 G，但数量有限，不超过 256 个。

  1. 全局队列（Global Queue）：存放等待运行的G。
  2. P的本地队列：同全局队列类似，存放的也是等待运行的G，存的数量有限，不超过256个。新建G’时，G’优先加入到P的本地队列，如果队列满了，则会把本地队列中一半的G移动到全局队列。
  3. P列表：所有的P都在程序启动时创建，并保存在数组中，最多有GOMAXPROCS(可配置)个。
  4. M：线程想运行任务就得获取P，从P的本地队列获取G，P队列为空时，M也会尝试从全局队列拿一批G放到P的本地队列，或从其他P的本地队列偷一半放到自己P的本地队列。M运行G，G执行之后，M会从P获取下一个G，不断重复下去。

Goroutine调度器和OS调度器是通过M结合起来的，每个M都代表了1个内核线程，OS调度器负责把内核线程分配到CPU的核上执行。

G,P,M 的个数问题

  1. G（Goroutine）的个数：理论上无限制，因为goroutine比线程更轻量级。但实际上它们会受到系统可用内存的限制。

  2. P（Processor）的个数：默认设置为逻辑 CPU 数，但在高并发环境下，通常设置为逻辑CPU数的两倍，为了提高调度的并行性和效率。每个P都可以绑定到一个M上执行goroutine，而设置更多的P可以使得在某些M阻塞时，其他M仍然可以执行P上的goroutine，从而减少等待时间。P的实际数量由环境变量 GOMAXPROCS 决定，或者是由runtime的方法 GOMAXPROCS() 决定。这个值限制了同时运行的goroutine的数量，即在任何给定时间，最多只有 GOMAXPROCS 个goroutine在CPU上执行。

  3. M（Machine/Thread）的个数：动态创建和销毁：M的数量是动态变化的，Go运行时根据需要创建和销毁M。M与P的数量没有绝对关系，一个M阻塞，P就会去创建或者切换另一个M。

没有足够的M来关联P并运行其中的可运行的G。比如所有的M此时都阻塞住了，而P中还有很多就绪任务，就会去寻找空闲的M，而没有空闲的，就会去创建新的M。
M与P之间没有绝对的固定关系。**一个M可以绑定到任意P上执行goroutine，而当M阻塞时，它会释放其绑定的P，P随后会尝试绑定到其他空闲的M上。**因此，即使P的数量较少，也可能因为工作量窃取和M的动态创建而有大量的M存在（尽管这些M中的大多数可能在等待中）。

Go 调度器

Go Scheduler（调度器）是什么？

Go 调度器（Scheduler）负责管理 Goroutine 的创建、运行、调度和回收。
由于 Go 语言使用了 goroutine 这种轻量级线程，而 goroutine 的数量通常远远超过操作系统线程的数量，因此需要一个高效的调度器来 在少量的 OS 线程上调度大量的 goroutines，避免 goroutine 直接与 OS 线程绑定带来的开销。

调度器设计策略

复用线程

避免频繁的创建、销毁线程，而是对线程的复用。
1️⃣ Work Stealing（工作窃取）：当某个线程处理完自己的 G 任务，当P的本地队列为空时，优先从全局队列获取，如果全局队列为空时则通过work stealing机制从其他P的本地队列偷取G。

2️⃣ hand off 机制：释放 P，交给其他M，发生在 M 因系统调用（syscall）阻塞导致 CPU 资源浪费时，线程释放绑定的P，把P转移给其他空闲的线程执行。

3️⃣ 抢占式调度：防止计算密集型 Goroutine 长时间占用 CPU，发生在计算密集型任务占用 CPU 太久，G 运行时间过长独占 CPU，影响其他任务，无 I/O 阻塞。Go 运行时会定期检查，强制暂停它并切换到其他 Goroutine，避免 CPU 被长时间占用。
在 Go 1.14 之前和 coroutine 中，要等待一个协程主动让出CPU才执行下一个协程。而一个Goroutine最多占用CPU 10ms，这就是 Goroutine 不同于 coroutine 的一个地方。

4️⃣ 局部性原则（Locality）：。Go 采用 P 维护本地运行队列，让 Goroutine 尽量在同一个线程上执行，减少线程切换开销，避免全局竞争，只有当 P 的队列为空时，才从全局队列或其他 P 窃取任务。

📌 调度流程

  1. 创建 Goroutine：
    当通过 go func() 创建新的 Goroutine 时，Goroutine 会首先被加入到与当前 P 关联的本地队列中。如果 P 的本地队列已满（超过256个 Goroutine），则新的 Goroutine 会被放入全局队列。
  2. 调度与执行：
  • Goroutine 只能运行在 M 中，每个 M 与一个 P 绑定，M 从 P 的本地队列中获取一个 Goroutine 来执行。
  • 如果 P 的本地队列为空，M 会尝试从全局队列或其他P的本地队列中偷取（work stealing 机制）任务执行，保证 CPU 资源利用率。
  1. 系统调用与阻塞：
  • 当 Goroutine 执行过程中发生阻塞或系统调用，M 也会被阻塞。这时，P 会解绑当前的 M，并尝试寻找或创建新的 M 来继续执行其他 G。hand off（移交）机制
  • 阻塞结束后，原来的 M 会尝试重新绑定一个 P 继续执行，并放入到这个P的本地队列。如果获取不到P，那么这个线程M变成休眠状态，加入到空闲线程中，然后这个G会被放入全局队列中。

内存分配

内存分配原理

前言

程序中的数据和变量都会被分配到程序所在的虚拟内存中，内存包含两个重要区域：栈区和堆区。

  • 栈区：函数调用的参数、返回值以及局部变量，由编译器进行管理，会在函数调用结束后被回收。
  • 堆区：不同语言对堆区内存的管理方法不同，C++等会由使用者主动申请和释放内存，Go和Java会由使用者和编译器共同管理，堆中的对象由内存分配器分配并由垃圾收集器回收。
    栈区的分配和回收比堆区简单的多。

Golang 内存分配器借鉴 tcmalloc 思想

thread cache malloc 思想：在多线程模型下，尽量减少锁的竞争开销，来提高内存分配的效率。
TCMalloc 采用 分级管理 + 线程缓存 的方式，将内存分配分为以下三个层级：

  1. Thread Cache（线程缓存）：每个线程维护一个私有的小块内存池（Thread Cache），直接从这里分配小对象，在这里避免了全局锁竞争。Thread Cache 中对于每一个 size class 维护一个单独的 FreeList，缓存还没有分配的空闲对象。
  2. Central Cache（中心缓存）：如果 Thread Cache 中没有合适的块，就向 Central Cache（全局缓存） 申请批量的小块内存。Central Cache 中同样对于每一个 size class 维护一个单独的 FreeList，但是是所有线程公用的，分配时需要加锁。
  3. Page Heap（页堆）：如果 Central Cache 也无法提供，就从 Page Heap（基于页的堆）申请内存，甚至向操作系统申请大块内存。能来自于 PageHeap 的缓存，也可能是 PageHeap 从操作系统中申请的新的内存。
    tcmalloc 为什么快：
  4. Thread Cache 减少了锁的竞争。
  5. 内存分配器会事先一次性申请一大块内存，减少系统调用的上下文切换成本。

Golang 的内存管理组件

go 内存分配思想

每一个处理器（P）都会分配一个线程缓存 mcache 用于处理微对象和小对象的分配，它们会持有内存管理单元 mspan，每个类型的 mspan 都会管理特定大小的对象。当 mspan 中不存在空闲对象时，它们会从 mcentral 对应的链表中申请新特点大小的 mspan。如果 mcentral 中也没有，会继续向下一层 mheap 中申请，mcentral 属于全局的堆结构体 mheap，mheap 会从操作系統中申请内存，mheap 管理多个 heap arena，每个 heap arena 都是一段连续的内存，对应操作系统中的 pages。

内存管理单元 mspan

每个 mspan 都对应一个大小等级（67种），由 一个或多个 arena 页组成。小对象类型的堆对象会根据其大小分配到相应设定好大小等级 mspan 上分配内存。

  • 微对象（0，16B）- 先使用微型分配器，再依次尝试线程缓存、中心缓存和堆分配内存；
  • 小对象［16B，32KB］- 依次尝试使用线程缓存、中心缓存和堆分配内存；
  • 大对象（32KB，+∞）- 直接在堆上分配内存，向 MHeap 申请 page；

mcentral

cache 作为线程的私有资源为单个线程服务，而 central 则是全局资源，为多个线程服务，当某个线程内存不足时会向 central 申请，当某个线程释放内存时又会回收进 central。

  2. 从nonempty列表获取一个可用span，并将其从链表中删除
  3. 将取出的span放入empty链表
  4. 将span返回给线程
  5. 解锁

  8. 将span从empty列表删除
  9. 将span加入noneempty列表
  10. 解锁

mheap 全局堆

从 mcentral 数据结构可见，每个 mcentral 对象只管理特定的 size class 规格的 span。每种 size class 都会对应一个 mcentral，这个 mcentral 的集合存放于 mheap 数据结构中。

从数据结构可见，mheap 管理着全部的内存，事实上Golang就是通过一个mheap类型的全局变量进行内存管理的。系统预分配的内存分为spans、bitmap、arean三个区域，通过mheap管理起来。其中 arena 即为所谓的堆区，应用中需要的内存从这里分配。其中 spans 和 bitmap 是为了管理 arena 区而存在的。

  • arena 的大小为512G，为了方便管理把 arena 区域划分成一个个的 page，每个 page 为8KB,一共有512GB/8KB个页；
  • spans 区域存放 span 的指针，每个指针对应一个或多个 page，所以 span 区域的大小为(512GB/8KB)*指针大小8byte = 512M；
  • bitmap 区域大小也是通过 arena 计算出来，不过主要用于GC。

以申请size为n的内存为例，分配步骤如下：

  1. 获取当前线程的私有缓存mcache
  2. 根据size计算出适合的class的ID
  3. 从mcache的alloc[class]链表中查询可用的span
  4. 如果mcache没有可用的span则从mcentral申请一个新的span加入mcache中
  5. 如果mcentral中也没有可用的span则从mheap中申请一个新的span加入mcentral
  6. 从该span中获取到空闲对象地址并返回

垃圾回收

垃圾回收原理

垃圾回收的核心就是标记出哪些内存还在使用中（即被引用到），哪些内存不再使用了（即未被引用），把未被引用的内存回收掉，以供后续内存分配时使用。垃圾回收的目标就是把那些已经分配的但没有对象引用的内存找出来并回收掉。
垃圾回收开始时从root对象开始扫描，把root对象引用的内存标记为”被引用”，考虑到内存块中存放的可能是指针，所以还需要递归的进行标记，全部标记完成后，只保留被标记的内存，未被标记的全部标识为未分配即完成了回收。

标记清除(Mark)

前面介绍内存分配时，介绍过span数据结构，span 中维护了一个个内存块，并由一个位图 allocBits 表示每个内存块的分配情况。在span数据结构中还有另一个位图 gcmarkBits 用于标记内存块被引用情况。

  1. 标记阶段对每块内存进行标记，gcmarkBits 有对象引用的的内存标记为1，没有引用到的保持默认为0。
  2. allocBits 和 gcmarkBits 数据结构是完全一样的，标记结束就是内存回收，回收时将 allocBits 指向 gcmarkBits ，则代表标记过的才是存活的，gcmarkBits 则会在下次标记时重新分配内存，非常的巧妙。

三色标记法

前面介绍了对象标记状态的存储方式，还需要有一个标记队列来存放待标记的对象，可以简单想象成把对象从标记队列中取出，将对象的引用状态标记在span的gcmarkBits，把对象引用到的其他对象再放入队列中。

这里的三色，对应了垃圾回收过程中对象的三种状态：

  • 白色（不可达）：初始状态下所有对象都是白色的，表示尚未被标记的对象，最终将会在本次GC中被清理。
  • 灰色（待扫描）：已被标记为存活，但它的子对象还未全部检查。等待进一步遍历其子对象。
  • 黑色（可达）：已经被标记为存活，并且它的所有子对象也都被标记。不会再被扫描，确定不会被回收。

三色标记法的执行过程可以分为 三个阶段：

  • 初始阶段：GC 从 “根对象”（Root Set，如全局变量、栈变量等）开始遍历。根对象被标记为 “灰色”，表示它们存活，但子对象还未检查。
  • 遍历标记阶段：选取 一个 “灰色” 对象，将它的子对象标记为 “灰色”，然后把它本身变成 “黑色”。不断重复，直到所有的对象都变成 “黑色” 或 “白色”。
  • 清理阶段：所有仍然是 “白色” 的对象都会被回收，因为它们不可达。”黑色” 对象不会被回收，它们仍然存活。

Stop The World

对于垃圾回收来说，回收过程中也需要控制住内存的变化，否则回收过程中指针传递会引起内存引用关系变化，如果错误的回收了还在使用的内存，结果将是灾难性的。

Golang中的STW（Stop The World）就是停掉所有的goroutine，专心做垃圾回收，待垃圾回收结束后再恢复goroutine。

STW时间的长短直接影响了应用的执行，为了缩短STW的时间，Golang不断优化垃圾回收算法，这种情况得到了很大的改善。

逃逸分析

Golang中逃逸现象, 变量“何时栈?何时堆?”

什么是逃逸分析？

Golang中一个函数内局部变量，不管是不是动态new出来的，它会被分配在堆还是栈，是由编译器做逃逸分析之后做出的决定。逃逸分析（Escape analysis）是指由编译器决定 变量应该分配在栈上还是堆上 的优化技术。

  • 如果编译器发现一个变量的生命周期 仅限于当前函数内部，就会 分配在栈上，这样 分配和释放都很快。
  • 如果变量 可能在函数返回后仍然被引用，比如被外部函数或 goroutine 使用，则 分配在堆上，并由垃圾回收 (GC) 负责管理。

什么是内存逃逸？

1)本该分配到栈上的变量，跑到了堆上，这就导致了内存逃逸。
2)栈是高地址到低地址，栈上的变量，函数结束后变量会跟着回收掉，不会有额外性能的开销。
3)变量从栈逃逸到堆上，如果要回收掉，需要进行 gc，那么 gc 一定会带来额外的性能开销。编程语言不断优化 gc 算法，主要目的都是为了减少 gc 带来的额外性能开销，变量一旦逃逸会导致性能开销变大。

内存逃逸的场景

  1. 方法内返回局部变量指针：返回局部变量指针，本身为一指针，其指向的内存地址不会是栈而是堆，这就是典型的逃逸案例。
  2. 切片（扩容后）长度太大：当栈空间不足以存放当前对象时或无法判断当前切片长度时会将对象分配到堆中。
  3. 在 interface 类型上调用方法：很多函数参数为interface类型，比如fmt.Println(a …interface{})，编译期间很难确定其参数的具体类型，也会产生逃逸。
  4. 在闭包中引用包外的值：闭包本质上是一个函数，但它能 记住 并 使用 它定义时所在作用域中的 变量，即使这个作用域已经结束。
  5. 向 channel 发送指针数据。
  6. 在 slice 或 map 中存储指针。

垃圾回收和逃逸分析

Go的垃圾回收，让堆和栈对程序员保持透明。真正解放了程序员的双手，让他们可以专注于业务，“高效”地完成代码编写。把那些内存管理的复杂机制交给编译器，而程序员可以去享受生活。

逃逸分析这种“骚操作”把变量合理地分配到它该去的地方。即使你是用new申请到的内存，如果我发现你竟然在退出函数后没有用了，那么就把你丢到栈上，毕竟栈上的内存分配比堆上快很多；反之，即使你表面上只是一个普通的变量，但是经过逃逸分析后发现在退出函数之后还有其他地方在引用，那我就把你分配到堆上。

如果变量都分配到堆上，堆不像栈可以自动清理。它会引起Go频繁地进行垃圾回收，而垃圾回收会占用比较大的系统开销（占用CPU容量的25%）。

堆和栈相比，堆适合不可预知大小的内存分配。但是为此付出的代价是分配速度较慢，而且会形成内存碎片。栈内存分配则会非常快。栈分配内存只需要两个CPU指令：“PUSH”和“RELEASE”，分配和释放；而堆分配内存首先需要去找到一块大小合适的内存块，之后要通过垃圾回收才能释放。

通过逃逸分析，可以尽量把那些不需要分配到堆上的变量直接分配到栈上，堆上的变量少了，会减轻分配堆内存的开销，同时也会减少gc的压力，提高程序的运行速度。

内存泄漏

什么是内存泄露

内存泄漏指的是 程序运行过程中，已分配的内存没有被正确释放，导致内存占用 持续增长，最终可能 耗尽可用内存，影响程序稳定性。

Go 语言有 垃圾回收 (GC, Garbage Collection)，但这并不意味着 不会发生内存泄漏。Go 不能自动释放仍然被引用的对象，如果代码逻辑不当，仍然会导致内存泄漏。

go 中的内存泄漏一般都是 goroutine 泄漏，就是 goroutine 没有被关闭，或者没有添加超时控制，让 goroutine 一只处于阻塞状态，不能被 GC。

常见的 Go 内存泄漏场景

  • 如果 goroutine 在执行时被阻塞而无法退出，就会导致 goroutine 的内存泄漏，一个 goroutine 的最低栈大小为 2KB，在高并发的场景下，对内存的消耗也是非常恐怖的。

  • 互斥锁（Mutex）未释放，sync.Mutex 或 sync.RWMutex 发生 死锁，goroutine 阻塞，导致内存泄漏。

  • time.Ticker 不会自动释放，如果不调用 Stop()，会持续占用内存。

  • 字符串 & 切片截取，Go 的字符串和切片 共享底层数组，导致原数据 不会被回收。

  • 数组传参，Go 语言按值传递，如果数组很大，传参会 占用大量内存，导致 临时性内存泄漏。

排查方式

一般通过 pprof 是 Go 的性能分析工具，在程序运行过程中，可以记录程序的运行信息，可以是 CPU 使用情况、内存使用情况、goroutine 运行情况等，当需要性能调优或者定位 Bug 时候，这些记录的信息是相当重要。

总览：go 编译和运行的完整过程

1️⃣ 编写 Go 源代码

使用 .go 扩展名的文件编写代码。

2️⃣ 编译过程

将源代码（.go 文件）转换为可执行文件，Go 编译过程大致可以分为以下几个步骤：

  1. 源代码解析：编译器首先读取 .go 源代码文件。语法解析器（Parser）对源代码进行词法分析，检查源代码是否符合 Go 语言的语法规则。

  2. 语法树生成：编译器将源代码转换为语法树（AST，Abstract Syntax Tree），即代码的结构化表示。AST 是语法分析的结果，表示程序的各个组成部分，如函数、变量、结构体等。

  3. 类型检查：在这一步，编译器会检查变量和函数等元素的类型是否匹配，确保符合 Go 语言的类型系统。Go 是强类型语言，编译器会检测类型错误，比如将整数赋给字符串类型的变量。

  4. 中间代码生成：编译器会将语法树转换为中间表示（IR），这是一种简化的、与硬件无关的代码形式，比源代码更加简洁。。中间代码用于后续的优化和生成机器代码。

  5. 优化：编译器在中间表示上进行一些优化，如死代码消除（removal of unreachable code）和常量折叠（constant folding）等。这些优化有助于提高程序的执行效率。

  6. 生成目标代码：编译器将中间代码转化为特定平台的机器码，通常为目标操作系统（如 Windows、Linux）和架构（如 x86 或 ARM）特定的二进制可执行文件。编译器会生成一个静态或动态链接的目标文件。

  7. 链接：编译过程是针对单个文件进行的，文件与文件之间不可避免地要引用定义在其他模块的全局变量或者函数，这些变量或函数的地址只有在此阶段才能确定。链接过程就是要把编译器生成的一个个目标文件链接成可执行文件。链接器将目标文件中的代码与 Go 运行时（Runtime）、标准库及外部库链接，生成最终的可执行文件。由于 Go 是编译成静态链接的二进制文件（除非手动指定使用共享库），所有依赖的库都被嵌入到最终的可执行文件中。

3️⃣ 执行过程

前言：Go 程序的执行由两层组成：Go Program，Runtime。它们之间通过函数调用来实现内存管理、channel 通信、goroutines 创建等功能。用户程序进行的系统调用都会被 Runtime 拦截，以此来帮助它进行调度以及垃圾回收相关的工作。

  1. 加载执行文件：操作系统加载程序的二进制代码到内存中，并启动程序的入口点（main 函数）。

  2. Go 运行时初始化：Go 程序的运行时（runtime）开始初始化，设置内存管理、垃圾回收器、调度器等。程序的 main 函数开始执行，并初始化相关的变量和资源。

  3. 调度（Scheduler）：Go Runtime 开始管理 goroutines。Go 使用 M:N 调度模型，将多个 goroutines 映射到操作系统线程上。运行时通过抢占式调度和协作式调度确保程序并发执行。

  4. Goroutine 执行：每个 goroutine 都有自己的栈，Runtime 负责管理所有 goroutines 的创建、调度和执行。当 goroutine 执行过程中发生阻塞（如等待 I/O、同步等），调度器会切换到其他可运行的 goroutine。

  5. 内存管理和垃圾回收：Runtime 管理内存分配和释放。通过垃圾回收机制（GC）自动清理不再使用的内存，减少内存泄漏的风险。

  6. 处理 I/O 和信号：Go Runtime 通过 I/O 多路复用（如 epoll、kqueue 等）和信号处理来支持高效的网络和 I/O 操作。

  7. 程序退出：当 main 函数执行完毕，Go 程序的执行完成，程序退出。Runtime进行清理工作，如关闭文件、释放资源等。
