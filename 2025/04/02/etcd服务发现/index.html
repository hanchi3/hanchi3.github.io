etcd服务注册与发现

Created2025-04-02|Updated2025-04-02
|Word Count:1.8k|Reading Time:5mins|Post Views:

etcd

etcd 是一个分布式键值存储数据库，支持跨平台，拥有强大的社区。etcd 的 Raft 算法，提供了可靠的方式存储分布式集群涉及的数据。etcd 广泛应用在微服务架构和 Kubernates 集群中，不仅可以作为服务注册与发现，还可以作为键值对存储的中间件。

键值对存储

从其定义来看，etcd 是一个「键值存储」的组件，存储是 etcd 最基本的功能，其他应用场景都是建立在 etcd 的可靠存储上。etcd 的存储有如下特点：

  • 采用键值对数据存储，读写性能一般高于关系型数据库；
  • etcd 集群分布式存储，多节点集群更加可靠；
  • etcd 的存储采用类似文件目录的结构：
    • 叶子节点存储数据，其他节点不存储，这些数据相当于文件；
    • 非叶节点一定是目录，这些节点不能存储数据。
      比如 Kubernetes 将一些元数据存储在 etcd 中，将存储状态数据的的复杂工作交给 etcd，Kubernetes 自身的功能和架构能够更加专注。

服务注册与发现

分布式环境中，业务服务多实例部署，这个时候涉及到服务之间调用，就不能简单使用硬编码的方式指定服务实例信息。服务注册与发现就是解决如何找到分布式集群中的某一个服务（进程），并与之建立联系。

服务注册与发现涉及三个主要的角色：服务请求者、服务提供者和服务注册中心。

服务提供者启动的时候，在服务注册中心进行注册自己的服务名、主机地址、端口等信息；服务请求者需要调用对应的服务时，一般通过服务名请求服务注册中心，服务注册中心返回对应的实例地址和端口；服务请求者获取到实例地址、端口之后，绑定对应的服务提供者，实现远程调用。

etcd 基于 Raft 算法，能够有力地保证分布式场景中的一致性。各个服务启动时注册到 etcd 上，同时为这些服务配置键的 TTL 时间，定时保持服务的心跳以达到监控健康状态的效果。通过在 etcd 指定的主题下注册的服务也能在对应的主题下查找到。为了确保连接，我们可以在每个服务机器上都部署一个 Proxy 模式的 etcd，这样就可以确保访问 etcd 集群的服务都能够互相连接。

传统硬编码方式

手动指定 host:port 进行 grpc.Dial() 连接。
缺点

  • 强依赖固定地址端口，缺乏灵活性。如果服务动态扩展（比如负载均衡下多实例运行），无法自动发现新实例。
  • **连接管理问题。**代码里每次 grpc.Dial() 都会新建连接：没有连接池，可能导致过多 TCP 连接，影响性能。缺乏健康检查，如果目标服务不可用，客户端不会自动重试。

服务注册与发现的基本概念

服务注册与发现是微服务架构中的核心机制，用于解决服务之间动态定位的问题。传统的硬编码方式（如 localhost:8081）在分布式系统中不灵活，而 etcd 提供了一个集中式的、动态的解决方案。

  • 服务注册: 服务启动时，将自己的地址（如 IP:Port）注册到一个中心化的存储（如 etcd），通常以键值对的形式存储。
  • 服务发现: 客户端通过查询这个存储，获取目标服务的地址，然后与之建立连接。
  • 动态性: 服务端地址可以随时变化（例如服务重启、扩容、故障转移），客户端需要实时感知这些变化。

etcd 的核心原理

etcd 是一个分布式键值存储系统，具有以下特性，非常适合服务注册与发现：

  • 键值存储: 数据以键值对形式存储，例如 /services/user -> localhost:8081。
  • 一致性: 使用 Raft 算法保证分布式节点间数据一致。
  • Watch 机制: 客户端可以监听某个键的变化，实时获取更新。
  • 租约（Lease）: 支持为键绑定租约，超时未续约则自动删除，用于检测服务是否存活。

服务注册与发现的实现过程

以下是基于 etcd 的服务注册与发现的完整过程：

服务注册（服务端）

  • 服务启动:
    服务（例如你的用户服务）启动时，确定自己的监听地址（如 localhost:8081）。

  • 连接 etcd:
    使用 etcd 客户端库（如 go.etcd.io/etcd/client/v3）连接到 etcd 集群。

  • 注册地址:
    将服务地址写入 etcd，例如键 /services/user 的值为 localhost:8081。
    通常会为这个键绑定一个租约（Lease），比如 10 秒超时。

  • 心跳续约:
    服务定期（例如每 5 秒）向 etcd 发送心跳，续约租约。
    如果服务宕机，心跳停止，租约到期后 etcd 自动删除该键，表明服务不可用。

服务发现（客户端）

  • 连接 etcd:
    客户端初始化时，连接到 etcd 集群。

  • 查询服务地址:
    查询某个键（如 /services/user），获取当前可用的服务地址列表。
    例如，返回 localhost:8081。

  • 建立连接:
    使用查询到的地址与服务建立连接（例如 gRPC 的 Dial）。

  • 监听变化:
    使用 etcd 的 Watch 机制，监听 /services/user 的变化。
    如果服务地址更新（新增、删除），客户端实时感知并调整连接。

动态更新

  • 服务扩容: 新实例启动并注册（如 /services/user -> [localhost:8081, localhost:8082]）。

  • 服务故障: 某实例宕机，租约到期，etcd 删除其地址，客户端感知后停止使用。

  • 客户端反应: 客户端根据最新的地址列表更新连接，可能涉及负载均衡。

在 gRPC 中的实现原理

gRPC 提供了一个 resolver 接口，用于实现自定义的服务发现逻辑。结合 etcd，过程如下：

gRPC Resolver

  • Resolver 的作用: 将服务名称（例如 etcd:///services/user）解析为具体的地址（如 localhost:8081），并动态更新。

  • 自定义 Resolver:
    实现 resolver.Builder 接口，定义如何从 etcd 获取地址。
    实现 resolver.Resolver 接口，处理地址解析和更新。

工作流程

  • 客户端初始化:
    注册一个 etcd resolver，告诉 gRPC 使用 etcd 解析服务地址。
    调用 grpc.Dial("etcd:///services/user", ...)。

  • Resolver 查询:
    Resolver 从 etcd 获取 /services/user 的值（例如 localhost:8081）。
    将地址传递给 gRPC 的连接管理器（ClientConn）。

  • 动态监听:
    Resolver 使用 etcd 的 Watch 监听键变化。
    地址更新时，通知 gRPC 更新连接目标。

  • 负载均衡:
    如果返回多个地址，gRPC 可通过内置负载均衡策略（如 round_robin）分发请求。
