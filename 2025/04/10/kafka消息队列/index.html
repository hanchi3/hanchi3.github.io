📌论坛项目架构 - 投票业务中的 kafka 消息队列

Created2025-04-10|Updated2025-04-10
|Word Count:2k|Reading Time:6mins|Post Views:

使用 Kafka 消息队列的原因

1 高并发处理

场景: 投票系统可能面临大量用户同时投票，例如热门帖子或活动期间的高峰流量。

Kafka 是一个分布式消息队列，支持高吞吐量（每秒处理数十万条消息），能轻松应对高并发请求。
相比 Redis 列表（如 vote_topic），Kafka 的分区机制允许并行处理，扩展性更强。

2 解耦前端与后端处理

场景: 用户投票后，前端需要快速响应，不能等待数据库写入等耗时操作。

Kafka 优势:
前端只需将投票数据发送到 Kafka 队列，后端异步消费，解耦了前端请求和数据库操作。
用户体验更好，避免了同步等待的延迟。

3 批处理优化

场景: 投票数据频繁写入数据库会导致性能瓶颈。

Kafka 优势:
消费者可以批量消费消息（如你的代码中 batchSize），减少数据库交互次数，提高效率。

4 分布式架构支持

场景: 你的项目是微服务架构（user-service, post-service, bff-service 等），需要跨服务协作。

Kafka 优势:
Kafka 支持分布式部署，允许多个生产者和消费者实例运行在不同节点。
通过消费组（Consumer Group），可以在多个 post-service 实例间负载均衡。

5 数据一致性

最终一致性，作用两次 redis。

pipeline 统一多个 redis 操作

  1. 原理

  • 批量发送命令：Redis 是一个单线程的服务，这意味着每个命令都会按顺序执行。客户端通过 Redis 提供的 pipeline 机制，将多个 Redis 命令打包成一个请求，统一发送给 Redis 服务端。

  • 服务器顺序执行：Redis 服务端按顺序执行这些命令。

  • 批量接收结果：客户端一次性接收所有命令的执行结果。

  1. 作用：

  • 减少网络延迟：避免了多次请求和响应的往返时间。客户端可以一次性发出多个命令，Redis 只需要返回一次结果。

  • 提升性能：通过减少网络往返，避免了每个操作都等待 Redis 响应。对于高并发的场景，使用 pipeline 可以极大地提升 Redis 的响应速度。

  • 原子性：使用 Redis pipeline 可以确保多个命令是按顺序执行的，但这些命令并不会立即被执行（直到 Exec 方法调用时），因此可以在一个事务中原子执行这些命令。

TxPipeline 本身并不提供事务级别的保证，命令执行是按顺序的，但不能保证“全部成功或全部失败”。如果某些命令失败，已成功的命令不会回滚。

如果需要完全的事务原子性，可以考虑使用 Redis 的 MULTI/EXEC 事务机制或者 Lua 脚本。其中 Lua 脚本提供了更强的原子性和控制，适合复杂的业务逻辑。

新架构的投票服务：不仅 redis，还涉及持久化

用户投票请求，调用 post-service 微服务，接口快速返回。

Vote 服务，/logic/post.go的Vote方法里：

  1. 将投票信息写入 redis 缓存（即上面旧架构的三个操作）；
  2. 标记为未入库：添加一个 redis key 为 vote:status:postID:userID，Set(voteStatusKey, status, expiration)；
  3. 打包投票信息 msg 发送到 kafka 队列；
    三个操作使用 Redis 的 SETNX 保持原子性。

后续逻辑处理，调用 Kafka 消费者服务，实现入库。

post-service/cmd/vote_consumer/main.go 这个服务通常作为后台进程独立运行，并且它不是通过 HTTP 请求与外界交互，而是与 Kafka 消息队列进行通信，实时处理投票信息。连接到 Kafka 集群，并监听指定的主题（如 post-votes）。处理从 Kafka 队列中获取到的投票消息。根据消息进行投票数据的更新，可能是更新数据库（如 MySQL）或缓存系统（如 Redis）。实现消息消费的逻辑，包括对消息的处理、错误日志、重试等。

  1. 监听 Kafka 消息队列，不断调用 ConsumeMessages 方法，是一个阻塞调用，意味着它会一直等待并接收 Kafka 消息，直到上下文被取消或发生错误。
  2. 每当从 Kafka 消息队列中获取到一条新的消息时，它会触发回调函数 func(msg kafka.VoteMessage) error，并传入消息对象 msg。
  3. 回调函数会处理消息内容，批量写入 mysql 数据库， 更新 voteCounts 并写入 JSON 文件，在 redis 里标记为入库。
    事件驱动：通过回调函数，可以在消息到达时自定义业务处理逻辑，并且使得程序能够异步地处理消息，不需要等待每一条消息处理完毕之后才继续消费新的消息。

另外：写入 redis 缓存的三个打包操作需要执行两次，最终一致性。

  1. 用户投票时，系统会：
    调用 CreatePostVote() 在 Redis 中记录一份缓存（这是立即反馈，提高用户体验）；
    设置投票状态为 “未入库”；
    将投票信息封装成 VoteMessage 发给 Kafka。

  2. Kafka 消费者处理这条消息时，会：
    再次调用 CreatePostVote()。
    这时通常意味着你要将数据持久化，或再次写入 Redis，以确保最终一致性（比如做数据修正，或者用户快速连续操作导致的状态覆盖问题）。

分布式系统中的典型策略：幂等处理 + 最终一致性。

幂等性：即多次执行 CreatePostVote() 不会造成重复写入或数据错乱。
最终一致性：即便 Redis 在用户点击投票时已经记录，但也可能因为 Redis 缓存过期、写失败、用户网络闪断、Kafka重试等情况出现数据缺失，所以消费者这一步是“补一枪”，确保数据一定写入 Redis。

CreatePostVote() 是幂等设计：

  • 如果用户之前投过同样方向的票，这次调用也不会再变；
  • 如果方向不同，会覆盖更新；
  • 如果 Redis 有锁（如你 Vote() 中做的那样），也能防止并发写错。
