Hadoop是什么？

架构方面来说

Hadoop 是一个包含 分布式存储（HDFS）、资源调度（YARN） 和 批处理计算引擎（MapReduce） 的基础平台，其他分布式应用（如 Spark、Hive、Flink、HBase）可以运行在 Hadoop 上，或使用它的能力。

具体形态方面来说

Hadoop 是一个可以部署在多台计算机上的软件。部署了 Hadoop 软件的主机之间通过 Socket 进行通讯。下载 Hadoop，相当于下载了 HDFS + YARN + MapReduce + Common 工具集，一整套基础运行环境。

Socket 通信，本质上就是：通过 “IP 地址 + 端口号” 来唯一确定一端，然后建立连接、收发数据。Socket 编程就是你用代码自己写一套「服务器 + 客户端」通信逻辑，让两台计算机通过 IP + 端口收发数据。封装了底层的 TCP/IP协议，让程序员可以像操作文件一样进行网络通信。

  • IP 地址：确定是哪台主机，比如 192.168.1.10
  • 端口号：确定主机上哪一个具体的程序/服务，比如 8080

HDFS

HDFS 是什么？

HDFS 是一个分布式的、高容错的文件系统，特别适用于存储海量数据并支持高吞吐量的数据访问。以守护进程方式启动，HDFS 客户端通过 Socket 与守护进程通信。

  1. 面向大文件
    适合存储 TB、PB 级超大规模文件，优化了大文件管理。

  2. 流式数据访问
    一次写入，多次读取，顺序读写为主，适合高吞吐量需求。

  3. 数据块存储
    将文件拆成固定大小（默认 128MB/256MB）的块，分散存储在多台机器上，支持并行读写。

  4. 高容错与自动恢复
    每个数据块有多个副本，节点故障时可自动从其他副本恢复，不丢数据。

  5. 高扩展性
    通过简单增加节点即可水平扩展，适应数据量增长。

  6. 数据本地性优化
    计算尽可能在数据所在节点进行，减少网络传输，加快处理速度。

  7. 简单一致的架构
    NameNode 管理元数据，DataNode 存储实际数据，整体架构清晰，维护方便。

HDFS 的读写流程

1️⃣ 写数据流程

  1. 客户端向 NameNode 申请写文件。

  2. NameNode 检查 有没有同名文件？有没有权限？如果一切正常，NameNode在内存里（而不是磁盘）暂时记录下这个文件的信息，状态是「未完成」。 →

  3. 同意后，选择合适的3个 DataNode，告诉客户端这3个节点的地址，返回可以写入的 DataNode列表。

  4. 客户端把数据切成块 Block（128MB），按顺序，通过**管道流（Pipeline）**传 Block 给第一个 DataNode，

    • 客户端开始往第一个 DataNode（比如 DN1）写第一块 Block 数据。
    • DN1接收到后，一边写本地磁盘，一边转发到下一个 DataNode（比如 DN2）。
    • DN2接着转发到第三个 DataNode（比如 DN3）。

  5. 以Packet（512字节）为单位，dn1收到一个Packet就会传给dn2，dn2传给dn3；dn1每传一个packet会放入一个应答队列等待应答。每个 DataNode 写完数据块后，会发送 ack（确认信息） 回客户端。

  6. 客户端收到所有 ack，确认该 Block 写成功。

  7. 当一个Block传输完成之后，客户端再次请求NameNode上传下一个Block的服务器。（重复执行2-6步）。

  8. 全部写完后，NameNode这时正式在元数据中记录这个文件：文件名、Block列表、各Block在哪些DataNode上有副本。

注意：

  • NameNode不负责数据的写入，只负责元数据记录和权限审批
  • 数据块副本的复制工作，由DateNode之间自行完成（构建一个PipLine，按顺序复制分发）
  • 客户端直接向一台DateNode写数据，这个DateNode一般是离客户端最近（网络距离）的那一个。机架感知：当文件副本数为三时，HDFS的放置策略是，如果写入程序位于数据节点上，则将一个副本放置在本地机器上，否则放置在与写入程序位于同一机架中的随机数据节点上、另一个副本放在不同（远程）机架中的节点上，最后一个副本则放在同一远程机架中的不同节点上。

2️⃣ 读数据流程

  1. 客户端向NameNode发起请求读取某文件。

  2. NameNode 检查：这个文件存不存在？用户有没有权限？

  3. 如果一切正常，NameNode返回：文件所有的 Block 列表。每个 Block 所在的 DataNode 列表（副本信息）。

  4. 客户端根据 NameNode返回的列表，从中选一个最近的 DataNode（比如同一台机、同一机架）。就近原则

  5. 客户端建立 Socket 连接到 DataNode。DataNode 按照 Block → Packet的顺序，一小块一小块把数据发送给客户端。每个 Packet 都会校验，发现损坏马上重试。

  6. 客户端以Packet为单位接收，先在本地缓存，然后写入目标文件。

注意：

  • 不管是都还是写，NameNode都不经手数据，均是客户端和DataNode直接通讯，不然对NameNode的压力太大
  • NameNode做授权判断（是否能写、是否能读）
  • 客户端直连DataNode进行写入、客户端直连DataNode进行block读取

NameNode和SecondaryNameNode

1️⃣ NN（NameNode）的作用

  1. 管理元数据
    记录「哪些文件存在」「这些文件被切成哪些Block」「Block在哪些DataNode上有副本」。
    这些数据存在于：
    fsimage（镜像文件，开机时加载）
    edits（操作日志，记录每次创建/删除/修改文件的动作）

  2. 处理客户端请求
    当客户端要读、写文件时，先找 NameNode。
    NameNode查元数据，告诉客户端该去哪个DataNode。

  3. 内存存储 + 周期性持久化
    NameNode大部分元数据都放在内存中（为了快），
    定期把内存中的最新状态刷到磁盘（就是新的 fsimage）。

  4. 高可用的重要性
    NameNode一旦挂了，整个HDFS就不可用！
    （这也是后来 HDFS 引入 HA（高可用 NameNode 双机热备）的原因）

2️⃣ NN和2NN工作机制

思考：产生2NN 的原因

首先，我们做个假设，如果存储在NameNode节点的磁盘中，因为经常需要进行随机访问，还有响应客户请求，必然是效率过低。因此，1.元数据需要存放在内存中。但如果只存在内存中，一旦断电，元数据丢失，整个集群就无法工作了。因此产生2.在磁盘中备份元数据的FsImage。

这样又会带来新的问题，当在内存中的元数据更新时，如果同时更新FsImage，就会导致效率过低，但如果不更新，就会发生一致性问题，一旦NameNode节点断电，就会产生数据丢失。因此，引入Edits文件（只进行追加操作，效率很高）。每当元数据有更新或者添加元数据时，修改内存中的元数据并追加到Edits中。这样，一旦NameNode节点断电，可以通过FsImage和Edits的合并，合成元数据。

但是，如果长时间添加数据到Edits中，会导致该文件数据过大，效率降低，而且一旦断电，恢复元数据需要的时间过长。因此，需要定期进行FsImage和Edits的合并，如果这个操作由NameNode节点完成，又会效率过低。因此，引入一个新的节点SecondaryNamenode，专门负责周期性地「整理fsimage+edits，生成新的fsimage快照」。

第一阶段：NameNode启动
第一次启动NameNode格式化后，创建Fsimage和Edits文件。如果不是第一次启动，直接加载编辑日志和镜像文件到内存。
客户端对元数据进行增删改的请求。
NameNode记录操作日志到磁盘，更新滚动日志。
NameNode在内存中对元数据进行增删改。

第二阶段：Secondary NameNode工作
Secondary NameNode询问NameNode是否需要CheckPoint。直接带回NameNode是否检查结果。
Secondary NameNode请求执行CheckPoint。
NameNode滚动正在写的Edits日志。
将滚动前的编辑日志和镜像文件拷贝到Secondary NameNode。
Secondary NameNode加载编辑日志和镜像文件到内存，并合并。
生成新的镜像文件fsimage.chkpoint。
拷贝fsimage.chkpoint到NameNode。
NameNode将fsimage.chkpoint重新命名成fsimage。

每次NameNode启动的时候都会将FsImage文件读入内存，加载Edits里面的更新操作，保证内存中的元数据信息是最新的、同步的，可以看成NameNode启动的时候就将FsImage和Edits文件进行了合并。

DataNode

1️⃣ DataNode工作机制

  1. 一个数据块在DataNode上以文件形式存储在磁盘上，包括两个文件，一个是数据本身，一个是元数据包括数据块的长度，块数据的校验和，以及时间戳。
  2. DataNode启动后向NameNode注册，通过后，周期性（6小时）的向NameNode上报所有的块信息。
    • DN向NN汇报当前解读信息的时间间隔，默认6小时；
    • DN扫描自己节点块信息列表的时间，默认6小时
  3. 心跳是每3秒一次，心跳返回结果带有NameNode给该DataNode的命令 如复制块数据到另一台机器，或删除某个数据块。如果超过10分钟没有收到某个DataNode的心跳，则认为该节点不可用。

MapReduce

1️⃣ 设计思想

核心思想是：简化并行计算、容错性。

  • MapReduce 通过将输入数据分割成多个小块，在不同的计算节点上并行处理数据，从而实现了数据的 并行处理。简化：通过提供简单的编程模型（Map 和 Reduce 函数），使开发者能够将复杂的分布式计算问题转化为简单的函数式编程问题。开发者只需专注于业务逻辑，如何在 Map 阶段处理数据和在 Reduce 阶段进行聚合，框架会处理其余的并行和分布式任务。

  • MapReduce 的设计强调 容错性，即使某个节点发生故障，计算过程仍然能够继续进行。这通过以下机制实现：

    • 数据备份：HDFS 在存储数据时会进行副本备份。如果某个数据节点故障，数据可以从其他副本中恢复。
    • 任务重试：如果某个 Map 或 Reduce 任务失败，MapReduce 框架会自动将该任务重新调度到其他节点执行。

2️⃣ 工作流程

划分输入数据：将输入数据拆分为多个数据块，每个数据块称为一个Input Split。
Map阶段：Map阶段是将输入数据转换为键值对（Key-Value pairs）的过程，也就是将输入数据映射为中间数据。
Shuffle阶段：Shuffle阶段将Map阶段输出的中间数据按照键进行分组，然后将相同键的所有值收集到一起。
Sort：每个分组的数据会根据键进行排序。这个过程保证了 Reduce 阶段处理的是已经排好序的键值对，方便后续的聚合操作。
Reduce阶段：Reduce阶段是将Shuffle阶段输出的中间数据进行聚合和计算的过程，最终输出最终结果。

3️⃣ 缺点

性能瓶颈：由于需要频繁的磁盘 I/O 操作（尤其是在 Shuffle 和 Sort 阶段），MapReduce 的性能较低，尤其是在需要进行多次迭代计算的应用中。

复杂逻辑编程复杂性：尽管 MapReduce 模型简单，但对于复杂的业务逻辑或数据处理需求，编写 Map 和 Reduce 函数可能比较困难。
