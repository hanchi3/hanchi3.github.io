采集与数仓的区别

完整项目数据流转过程

  1. 用户行为产生数据
    数据的起点是用户的操作，用户通过前端应用（比如 App、网页等）与系统进行交互，触发各种操作，比如点击、下单、支付等行为，这些操作会通过业务系统产生数据。

  2. 业务系统接收请求，生成数据，进入存储层
    用户请求经过业务服务器处理后，会生成两类数据：
    一类是核心的业务数据，比如用户下单、支付等结构化数据，这些会被存入 mysql业务关系型数据库。是企业正常运转的核心数据，反映了企业的实际业务操作。
    另一类是用户的行为数据（如点击日志、浏览记录），通常通过日志文件或埋点方式进行采集，以日志形式写入日志文件中。可用于行为分析、兴趣建模、个性化推荐等场景。

  3. 数据采集
    从mysql、log文件里同步取出，存入HDFS集群，作为数据仓库的数据源。

  4. 进入数据仓库，进行统计分析
    所有原始数据会通过采集、清洗、加工等步骤统一进入数据仓库（DWD/DWS层），用于统一建模、分析、查询。

  5. 数据输出到可视化平台
    最终，数据会通过可视化平台（如 BI 系统、DataV、大屏展示等）呈现给业务人员或管理层，用于支持运营分析与决策。也可能会输出给算法工程师，提供训练数据。也可能输出给产品经理，提供分析来源。

数据仓库的核心目标：统计分析

数据仓库的核心功能不是“存储数据”，而是“统计分析”。存储只是手段，统计分析才是目的。

可用于统计分析的技术框架包括：

  • MapReduce（MR）——早期技术
  • Spark
  • Flink（未来会学）
    在实际项目中，优先考虑 Spark，但直接用 RDD 编写复杂、开发成本高。使用 SQL 替代手写 RDD 提高开发效率。学习门槛更低，开发速度更快。

SQL 在 Spark 中的两条技术路线：

  • Spark on Hive：Spark 来解析 SQL
  • Hive on Spark：Hive 来解析 SQL
    区别在于 “谁来解析 SQL”
    实际开发中通常两个都用，但 Hive on Spark 更常见，特别在 Hadoop 环境下。

统计分析的基本步骤：
无论使用什么技术框架（Spark、Hive、MR），统计分析必须遵循以下基本步骤：

  1. 数据源对接
    明确数据来源（内存、磁盘、数据库、HDFS等）
  2. 数据加工（预处理）
    包括格式转换、过滤、去重、脱敏等，本质是为了让数据满足后续计算需求
  3. 统计
    执行聚合类操作，如求和、计数、最大/最小值等
  4. 分析
    在统计结果的基础上进行进一步筛选、排序、选取关键部分（如Top-N分析），为展示（如图表）提供支撑。
  5. 结果输出
    可选：保存到数据库、文件，或在控制台输出

数据仓库的数据源

为什么不直接用业务数据库作为数据仓库的数据源？

  1. 存储结构不匹配
    业务数据库（如 MySQL）：行式存储（Row-oriented）
    数据仓库：列式存储（Column-oriented）
    行列存储的结构不同，导致直接读取效率低、无法高效支持统计分析。
  2. 业务数据库中存储的不是海量数据，数据量不够，业务数据库只保留有限时间（如2年）的数据，无法满足数据仓库“分析10年数据”的需求。
  3. 数据仓库的大量查询操作会影响业务数据库的性能，进而影响业务系统正常运行。业务数据库不是为了数据仓库服务的，是为用户业务服务的。

正确做法：为数据仓库设计独立的数据源，独立、列式、海量、与业务库同步+归档

为什么每一步都要建很多表？

处理多需求（数百/千个），不建中间表每次从源头重新计算，重复读取海量数据。建中间表加工/统计结果缓存复用，极大提升效率。“一次加工，多次使用” —— 避免重复计算，提升整体吞吐。

数据采集和数据仓库解耦（用HDFS）

采集的本质：
原始数据来自不同的数据源（如业务数据库），我们需要将这些数据定期同步过来。这一过程被称为数据采集。数据采集不是一次性的，而是周期性同步，目前通常以“天”为单位进行同步（未来可支持小时级或实时同步）。采集的本质是将源系统的原始数据同步到数据仓库的“源表”中。

数据采集的耦合问题：
采集过程中存在一个关键问题：采集系统必须知道目标数据库中的表结构，否则无法将数据正确写入。这导致了采集系统与数据仓库之间出现了耦合性，表现为：

  • 采集系统必须依赖数据仓库中定义好的表结构；
  • 数据仓库的变更可能会影响采集项目的实现。
    但我们在架构设计中提倡：采集系统与数据仓库应能独立开发、部署，这就需要解耦设计。

解耦方案 —— 引入中间层：

    graph LR
    subgraph 采集项目
        M[MySQL] -->|DataX| F1[文件]
        L[日志文件] -->|Flume| F2[文件]
        F1 --> H[HDFS]
        F2 --> H
    end

    H -->|Load Data Inpath| T[数据仓库表]

    subgraph 数据仓库项目
        T --> P[加工表] --> S[统计表] --> A[分析表]
    end
模块 角色 / 职责 依赖关系说明
采集项目 负责采集数据，并将数据写入 HDFS 文件，Flume / DataX / Maxwell 不关心表结构
数据仓库 使用 LOAD DATA 将 HDFS 文件加载为表，Hive SQL + 中间表设计 不关心数据来源，只依赖 HDFS 文件

HDFS 是天然解耦介质：

  • Hive 表底层 = HDFS 文件
  • 采集写文件 → 数仓读文件 → 零耦合

采集系统只需要将数据写入中间层，无需关心最终表结构；数据仓库系统从中间层读取数据，进行清洗、转换并加载到最终表中。解耦设计使得两个系统可以独立开发、灵活迭代，提升整体系统的可维护性与扩展性。

采集平台（可以满足离线数仓需求、实时数仓需求）

数据采集系统流程图

数据采集项目：

  • logFile通过Flume工具，先进入Kafka（自带offset可以均衡的取数据 平衡速率 主要为了实时数仓 离线数仓可以不用kafka），再通过Flume工具，进入Hadoop集群。File => Flume => Kafka => Flume => HDFS
  • Mysql业务数据通过增量同步Maxwell工具，进入Kafka，再通过Flume工具，进入Hadoop集群。每日全量DataX工具，进入Hadoop集群。增量同步 mysql => Maxwell => Kafka => Flume =>HDFS，全量同步 mysql => DataX => HDFS。

补充：

  • 采集不仅给离线数仓用，还要给实时数仓用，flink直接对接Kafka就行了。
  • 全量数据同步：表的全部数据。 增量数据同步：表的新增及变化的数据。 与统计需求挂钩。全量数据同步（DataX）不用于实时数据分析。增量数据同步（Maxwell）用于实时数据分析，也用于离线数据分析。

日志数据采集过程：

  1. jar包生成模拟日志数据app.log，
  2. flume路径下创建job的conf配置文件 file_to_kafka.conf，配置source和channel(用不到sink)，通过启动命令自动启动flume采集。推入Kafka topic_log。
  3. 再通过Flume将Kafka的数据同步到HDFS，（其实由于有Kafka，写入hdfs其实是实时的，但实际上离线数仓的取用是每日离线的）。（由于离线数仓采用Hive的分区表按天统计，为了方便所以HDFS目标路径要包含一层日期，Flume工具配置选择KafkaSource、FileChannel、HDFSSink），（KafkaSource订阅Kafka中的topic，增加拦截器：判断json格式数据是否有效，为Event修改header中的时间戳 解决零点漂移问题）（拦截器的jar包放到/flume/lib下）。

业务数据采集过程：

  1. mysql的增量数据通过Maxwell工具（监控mysql的binlog变化的实时流式工具），以json文件格式，推入Kafka topic_db。（采用每日增量同步的表，通常需要首次同步时全量一下，通过Maxwell的bootstrap工具（select *）来进行历史数据的首日全量同步）。Flume工具从Kafka里取数据，存入hdfs里/gmall/db/表名_inc/2022-06-06，（选择KafkaSource、FileChannel、HDFSSink），（也需要一个拦截器，从Event中找表名和日期）。
  2. mysql的全量数据通过DataX工具（基于Select查询的离线、批量同步工具）同步。不进入Kafka。（为了方便所以HDFS目标路径要包含一层日期，故hdfswriter的path参数值应该是动态的）。通过DataX工具，配置mysqlreader、hdfswriter插件的配置json文件，存入hdfs里/gmall/db/表名_full/2022-06-06。

全量同步与增量同步（仅业务mysql数据）

业务数据是状态，日志数据是事件；状态需要一致性同步，事件只需记录发生。

全量同步是指将某张表中的所有数据整体拷贝到目标系统中，适用于对整张表进行统计分析的场景，例如统计网站累计注册用户总数时，只需要一张完整的用户表即可进行简单高效的查询。而增量同步则是指只同步新增或发生变化的数据，适用于对数据变动有明确时间窗口要求的统计需求，例如统计最近一周新增注册用户数。如果仍使用全量同步，需要从庞大的数据集中筛选特定时间段的记录，不仅效率低下，还可能造成系统性能瓶颈。相反，如果使用增量同步，仅记录新增和变化的数据，则可以直接针对小数据集进行分析，效率更高，统计更灵活。
数据采集的方式必须服务于数据仓库建设和后续的统计分析目标，技术选型应以最终分析效果与效率为导向。

应用场景：
全量同步 在初始导入、灾备恢复、或数据表结构发生重大变化时，需要将整个表数据完整复制一次。
增量同步 日常更新中，订单状态变化、商品价格更新等，通常基于主键或时间戳记录变化部分，持续同步。

日志数据不区分全量、增量

1. 日志是天然“追加型”数据
2. 实时/准实时采集为主，不需要回溯历史
3. 日志不会用于事务性操作或覆盖原数据

业务数据的概念

✅ 业务数据 = 真实的交易流程产生的数据。
学习建议：每讲一个具体业务流程时（如“下单流程”），再讲解这个流程涉及到哪些数据表；从“操作动作”反推“数据流向”。

业务数据杂乱的原因：

  • 表太多，字段太多，关联性复杂；
  • 不同流程会涉及不同数据表（比如活动表、用户表、商品表、订单表等）；
  • 要完成一次有效的数据分析，必须熟悉这些表的结构与业务含义。

核心电商概念：SPU 与 SKU

概念 全称 含义 举例
SPU Standard Product Unit 标准产品单位，表示某种商品的“类” iPhone 手机
SKU Stock Keeping Unit 库存单位，表示具体销售的“单个商品” 深空灰 iPhone 13 128GB 5G
✅ 一般我们做销售统计、商品分析，分析的都是 SKU 级别数据。

平台属性 vs 销售属性

属性类型 含义 作用 示例
平台属性 用于查询与过滤 帮助筛选商品 品牌、分类、屏幕尺寸等
销售属性 用于购买时选择 区分具体的 SKU 颜色、内存、版本等

各个业务表的作用

表名 数据类型 说明 日志系统用途
user（用户表） 状态数据 存储用户静态信息（如昵称、性别、生日） 结合行为数据分析用户画像
product（商品表） 状态数据 存储商品静态信息（如名称、价格、种类、品牌） 分析用户对商品的偏好、曝光效果等
favor（收藏表） 状态数据（也可视为行为结果） 记录用户收藏商品的行为结果 分析用户兴趣、构建推荐系统
cart（购物车表） 状态数据（用户行为的当前状态） 记录用户加入购物车的商品和状态（数量、时间） 分析购买意向、转化漏斗中间状态

状态数据（业务表）提供用户/商品的上下文信息，行为日志则提供操作事件，两者结合可以实现更全面的用户行为分析。

优惠券业务（领用行为）

  • 优惠券信息表，存储优惠券本身的信息。
  • 优惠券领用表，记录用户和优惠券的领用/使用行为，包括领取时间、使用时间【下单时选用优惠券（可能未支付）】、实际支付时间【支付成功时才真正使用掉】。

➡️ 统计分析时会根据使用率、转化率、核销率等指标进行分析。

下单行为业务（订单行为采集）
下单流程简述：用户对某个商品进行下单行为，这时就涉及多个数据表的联动记录。
① 核心主表

  • user：用户表
  • product：商品表
  • order：订单主表（记录整笔订单的状态/时间）
    ② 明细表
  • order_detail（订单明细表）：一笔订单中可能包含多个商品，每个商品一条记录。
    ③ 辅助表（业务维度拓展）
  • order_status_log 订单状态流水记录（如：创建、支付、取消、退单等）
  • order_coupon_log 记录下单时使用的优惠券
  • order_activity_log 记录参与的活动（如双11、618）
  • order_region 地区信息（用于地域分布分析）

说明：各个表之间通过订单ID、用户ID等进行关联。通过多个维度（时间、地区、活动、使用优惠）来还原用户的购买行为轨迹。

维度 说明

采集平台具体用到的技术

零点漂移问题（日志）

这个问题出现在日志采集的完整流程中：日志文件原本在 2022年6月8日23:59:59 生成，并发送到 Kafka。Kafka 中的消息被 Flume 采集后写入 HDFS，HDFS 以时间为维度动态生成目录保存日志。然而问题在于，Flume 默认会使用当前系统时间作为事件时间戳，也就是说即使日志内容中的时间是 6 月 8 日 23:59:59，但由于采集和传输延迟，Flume 实际记录的时间可能是 6 月 9 日的 00:00:02，仅仅几秒钟的差异就会导致日志被保存到了错误的日期目录下。这种时间戳与实际日志生成时间不一致的现象就是所谓的“零点漂移问题”。

零点漂移问题的核心危害在于：日志被错误归档，进而影响下游数据分析的准确性，尤其是按日期分区的存储策略下更为严重。

为了解决该问题，需要引入一个 Flume 拦截器（Interceptor）。这个拦截器的作用是在事件继续传输之前，拦截并修改 event 中 header 的时间戳字段，将其替换为日志 body 中真实的时间字段，从而确保数据归档到正确的时间路径中。最终的流程变成：日志产生 → Kafka → Flume 拦截器调整时间戳 → 正确写入 HDFS 的对应时间目录。

FLume 拦截器开发代码解析

🧩 拦截器作用
Flume 拦截器（Interceptor）用于在数据从 Source → Channel → Sink 的过程中，对 Event 进行预处理。

🎯 当前任务目标
实现一个自定义的拦截器，主要完成两个功能：

  1. 验证 Event 的 JSON 格式是否合法
  2. 修正 header 中的时间戳，解决时间漂移问题

🔧 开发步骤说明
1️⃣ 加入依赖（Maven 依赖和 build 配置）,使用 mvn clean package 打包成包含依赖的 fat jar，供 Flume 加载。
2️⃣ 创建拦截器类

  • 包名如：com.gmail.flume.interceptor
  • 类名：TimestampInterceptor
  • 实现接口（重写接口的方法）：org.apache.flume.interceptor.Interceptor
    3️⃣ 拦截器逻辑核心：验证 & 修改
    使用 fastjson，异常即认为非法数据，非法数据通过 return null 丢弃。
    修改 Event 的 header，设置标准时间戳。

⚙️ Flume 配置文件修改
拦截器需要在 Flume 配置文件中进行声明，类型为 Java 类的 Builder 内部类路径。

📦 打包说明
执行命令：mvn clean package
输出的 jar 包需放置到 Flume 的 classpath 下（如：lib 目录）。
重新启动 Flume 后，拦截器才会生效。

DataX 异构数据源离线同步工具（业务：全量）

在全量表数据同步的场景中，DataX 是一个非常实用的采集工具。它是 阿里巴巴开源的异构数据源离线同步工具，支持将不同结构的数据（例如 JSON、Parquet、关系型数据库、列式存储等）进行结构转换并完成同步。这里的“异构”是指数据结构不同，例如 JSON 是行式结构，而 Parquet 是列式结构，普通用户如果手动转换难度较高，而 DataX 可以自动完成结构映射和转换。

DataX 更像是一个 中间件，实现了对源端与目标端的解耦。数据源和数据目标不需直接连接，而是都通过 DataX 来中转数据，这样做可以显著降低系统间的耦合度，提高灵活性与可维护性。

DataX 采用了 插件机制（Plug-in） 和 框架架构（Framework）。其工作方式类似于之前提到的 Flume 工具，即通过 Reader（读取器） 与 Writer（写入器） 插件来处理源端与目标端的数据对接，而框架则负责插件调度与数据传输控制。其运行方式依赖于配置文件，主要采用 JSON 格式 描述任务流程，非常灵活且可插拔。

运行流程简述：
1️⃣ 编写 JSON 配置文件（必须按规定格式）（核心）；
2️⃣ 使用如下命令执行任务：python datax.py your_job.json
3️⃣ DataX 会根据配置文件自动加载对应 reader/writer 插件，完成数据同步任务。

执行 DataX 命令：python bin/datax.py job/job.json。job.json 是一个标准的 JSON 配置文件，包含任务的读取与写入配置。

  1. reader（数据读取模块）：
    • 例如 mysqlreader 插件（内置插件），用于读取模拟数据。
    • 包括字段类型定义（如字符串、布尔、日期、字节等）。
    • 模拟读取 10 万条数据。
  2. writer（数据写入模块）：
    • 例如 hdfswriter 插件（内置插件），将读取的数据打印到控制台。
    • 指定编码方式（如 UTF-8），不打印内容本身，仅打印执行结果。

Maxwell（业务：增量）

Maxwell 是一个使用 Java 编写的开源工具，专门用于捕获 MySQL 数据库的变更操作（即增、删、改）。它能够实时监听数据库中数据的变更，并将这些变更数据以 JSON 格式发送到 Kafka 等消息队列中。这里的“变更操作”专指对数据内容造成影响的操作，例如 INSERT（插入）、UPDATE（更新）、DELETE（删除），而不包括查询类操作，因为查询并不改变数据内容。

要理解 Maxwell 的采集原理，先明白 MySQL 的数据写入机制和 Binlog（Binary Log）机制:
MySQL 是以查询为主的数据库，因此它的设计核心是如何提升查询效率。MySQL 为了查询更快，采用了内存缓存机制：
- 数据存储在磁盘，但经常查询的数据会加载进内存（称为“读缓存”）；
- 新写入的数据会先进入“写缓存”（尚未落盘）；
- 查询时会优先从“写缓存” → “读缓存” → “磁盘”依次查找。

为了提高写入效率，MySQL 采用延迟落盘策略：
- 写操作并不会立即写入磁盘，而是先写入“写缓存”；
- 当写缓存达到一定阈值或触发某个事件时，才将数据同步到磁盘。
⚠️ 这带来了一个问题：如果数据库突然崩溃或断电，缓存中的数据可能丢失。

为了防止写缓存中的数据丢失，MySQL 增加了 Binlog（二进制日志）：
- 每次写操作，都会首先顺序写入 Binlog；
- 然后再写入写缓存；
- 最后才同步到数据文件中。
Binlog 是顺序写的，而数据文件是随机写。顺序写相比随机写，性能更高且更可靠。

Maxwell 正是基于这一点：

  • Maxwell 作为一个 MySQL Binlog 的监听器；
  • 它通过连接到主库，监听 Binlog 中的事件（insert/update/delete）；
  • 然后将这些事件转化为结构化 JSON 格式的数据，发送到 Kafka、ES、RocketMQ 等系统中。

📌 注意：
Maxwell 只能用于 MySQL 主库开启了 Binlog 且格式为 ROW 模式；
不影响 MySQL 性能，是一种非侵入式、可靠的实时数据采集方式。

增量表

MySQL → Maxwell → Kafka topic(DB) → Flume → HDFS

目标路径的规则举例：/data/warehouse/db/activity_info/inc/2022-06-08/

Flume配置重点

  • source：配置Kafka source，订阅DB topic。
  • channel：用File Channel即可。
  • sink：配置HDFS sink，写数据到HDFS指定路径。
  • 路径中要动态拼接表名和日期，需要从Kafka消息头（header）中获取动态参数。

Flume拦截器作用
需要用Flume拦截器（Interceptor）对Kafka消息做处理；
拦截器从消息中提取表名、时间戳等字段，放入header，方便HDFS sink动态构造路径。

首日同步需要使用Maxwell的“bootstrap”功能来实现全量数据的同步。这个bootstrap功能通过在Maxwell中标记数据同步的开始和结束，确保首日全量数据完整导入。
