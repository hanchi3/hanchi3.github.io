Hadoop安装

1. 环境准备
将安装包上传到software文件夹中，解压，修改环境变量，分发环境变量。

2. 配置hadoop文件
进入/opt/module/hadoop/etc/hadoop/文件夹，修改多个xml文件，分发Hadoop（module文件夹），xsync /opt/module/hadoop/。

3. 启动集群
初始化初始化 NameNode（hadoop102）（module/hadoop文件夹）；HDFS+yarn启动指令，或使用统一启动命令：sbin/start-all.sh。

4. 集群管理脚本
创建 hdp.sh 脚本（位于 /opt/module/hadoop/bin/），支持启动/停止集群。

Zookeeper安装

1. 环境准备
将安装包上传到software文件夹中，解压，创建数据目录：在 /opt/module/zookeeper/ 下创建 zkData 文件夹。

2. 配置 ZooKeeper
设置节点标识：在 zkData 下创建 myid 文件，内容为节点唯一标识。
配置 zoo.cfg：进入 /opt/module/zookeeper/conf/，复制 zoo_sample.cfg 为 zoo.cfg，里面设置了数据目录、客户端端口、集群节点、其他参数。

3. 分发与配置调整
分发 ZooKeeper 目录到所有节点（hadoop102、hadoop103、hadoop104）：xsync zookeeper/。
在 hadoop103 和 hadoop104 上修改 myid 文件，分别设置为 3 和 4。

4. 启动集群
在每个节点上执行启动命令：bin/zkServer.sh start

5. 集群管理脚本
在bin文件夹中创建zk.sh 脚本，支持启动/停止集群。

1. 环境准备
将安装包上传到software文件夹中，解压。

2. 配置 Kafka
修改配置文件（kafka/config文件夹），编辑server.properties文件。

3. 分发与配置调整
分发安装包并修改hadoop103、hadoop104的broker.id及advertised.listeners。配置环境变量，分发变量，刷新变量（三台虚拟机）。

4. 启动集群
Kafka启动命令 bin/kafka-server-start.sh -daemon config/server.properties

5. 集群管理脚本
在bin文件夹中创建kf.sh，支持启动/停止集群。

采集与数仓的区别

完整项目数据流转过程

  1. 用户行为产生数据
    数据的起点是用户的操作，用户通过前端应用（比如 App、网页等）与系统进行交互，触发各种操作，比如点击、下单、支付等行为，这些操作会通过业务系统产生数据。

  2. 业务系统接收请求，生成数据，进入存储层
    用户请求经过业务服务器处理后，会生成两类数据：
    一类是核心的业务数据，比如用户下单、支付等结构化数据，这些会被存入 mysql业务关系型数据库。是企业正常运转的核心数据，反映了企业的实际业务操作。
    另一类是用户的行为数据（如点击日志、浏览记录），通常通过日志文件或埋点方式进行采集，以日志形式写入日志文件中。可用于行为分析、兴趣建模、个性化推荐等场景。

  3. 数据采集
    从mysql、log文件里同步取出，存入HDFS集群，作为数据仓库的数据源。

  4. 进入数据仓库，进行统计分析
    所有原始数据会通过采集、清洗、加工等步骤统一进入数据仓库（DWD/DWS层），用于统一建模、分析、查询。

  5. 数据输出到可视化平台
    最终，数据会通过可视化平台（如 BI 系统、DataV、大屏展示等）呈现给业务人员或管理层，用于支持运营分析与决策。

数据仓库的核心目标：统计分析

数据仓库的核心功能不是“存储数据”，而是“统计分析”。存储只是手段，统计分析才是目的。

可用于统计分析的技术框架包括：

  • MapReduce（MR）——早期技术
  • Spark
  • Flink（未来会学）
    在实际项目中，优先考虑 Spark，但直接用 RDD 编写复杂、开发成本高。使用 SQL 替代手写 RDD 提高开发效率。学习门槛更低，开发速度更快。

SQL 在 Spark 中的两条技术路线：

  • Spark on Hive：Spark 来解析 SQL
  • Hive on Spark：Hive 来解析 SQL
    区别在于 “谁来解析 SQL”
    实际开发中通常两个都用，但 Hive on Spark 更常见，特别在 Hadoop 环境下。

统计分析的基本步骤：
无论使用什么技术框架（Spark、Hive、MR），统计分析必须遵循以下基本步骤：

  1. 数据源对接
    明确数据来源（内存、磁盘、数据库、HDFS等）
  2. 数据加工（预处理）
    包括格式转换、过滤、去重、脱敏等，本质是为了让数据满足后续计算需求
  3. 统计
    执行聚合类操作，如求和、计数、最大/最小值等
  4. 分析
    在统计结果的基础上进行进一步筛选、排序、选取关键部分（如Top-N分析），为展示（如图表）提供支撑。
  5. 结果输出
    可选：保存到数据库、文件，或在控制台输出

数据源

为什么不直接用业务数据库作为数据仓库的数据源？

  1. 存储结构不匹配
    业务数据库（如 MySQL）：行式存储（Row-oriented）
    数据仓库：列式存储（Column-oriented）
    行列存储的结构不同，导致直接读取效率低、无法高效支持统计分析。
  2. 业务数据库中存储的不是海量数据，数据量不够，业务数据库只保留有限时间（如2年）的数据，无法满足数据仓库“分析10年数据”的需求。
  3. 数据仓库的大量查询操作会影响业务数据库的性能，进而影响业务系统正常运行。业务数据库不是为了数据仓库服务的，是为用户业务服务的；

正确做法：为数据仓库设计独立的数据源

数据采集和数据仓库解耦

采集的本质：
原始数据来自不同的数据源（如业务数据库），我们需要将这些数据定期同步过来。这一过程被称为数据采集。数据采集不是一次性的，而是周期性同步，目前通常以“天”为单位进行同步（未来可支持小时级或实时同步）。采集的本质是将源系统的原始数据同步到数据仓库的“源表”中。

数据采集的耦合问题：
采集过程中存在一个关键问题：采集系统必须知道目标数据库中的表结构，否则无法将数据正确写入。这导致了采集系统与数据仓库之间出现了耦合性，表现为：

  • 采集系统必须依赖数据仓库中定义好的表结构；
  • 数据仓库的变更可能会影响采集项目的实现。
    但我们在架构设计中提倡：采集系统与数据仓库应能独立开发、部署，这就需要解耦设计。

解耦方案 —— 引入中间层：
采集系统只需要将数据写入中间层，无需关心最终表结构；数据仓库系统从中间层读取数据，进行清洗、转换并加载到最终表中。解耦设计使得两个系统可以独立开发、灵活迭代，提升整体系统的可维护性与扩展性。
具体表现为：

  1. 数据采集：业务mysql数据通过 DataX、Maxwell 同步，业务file数据通过 Flume 同步，存入HDFS。
  2. 数据仓库：从HDFS里取数据源。（hdfs解耦合）
  3. 数据可视化：数据分析结果，又存入mysql，web从mysql里取数据。（mysql解耦合）

采集平台（可以满足离线数仓需求、实时数仓需求）

数据采集与数据流转架构

数据采集与流转体系需同时考虑离线和实时处理两种场景。

  1. 首先，从数据产生环节讲起，强调业务交互和用户行为产生原始数据，这些数据由业务服务器收集，并存储到业务数据库中。这里会涉及后端分布式负载均衡器的使用，SpringClould、go-Zero这类分布式业务框架，确保高可用性和扩展性。

  2. 接着，数据采集和同步环节，采用专门的服务将本地文件/业务数据库上传至分布式文件系统（如 HDFS），以实现解耦和统一管理。日志文件使用“Flume”作为文件上传工具，它在设计初期就是为了解决从本地向 HDFS 传输数据的问题，因此具备高度专业性。

  3. 引入了Kafka，指出 Kafka 的加入并非仅仅为了解决“削峰”问题（即缓冲高并发数据流），核心价值在于解耦上下游、支持可控消费、以及偏移量机制。Kafka支持从任意偏移位置消费数据，这使得生产与消费可以解耦，便于做容错和负载控制。因此，Kafka 是实时链路中数据传输的重要中间件。

  4. 此外还提到，从数据存储解耦层（如 HDFS）开始，数据被同步到数据仓库中（使用 Hive），再通过 HiveSQL 实现统计分析，构建离线分析模型。而为了实现数据的可视化展示，需将部分处理后的数据同步回 MySQL，便于可视化平台（如 BI 工具）接入查询与展示。

数据采集系统流程图

数据采集项目：

  • logFile通过Flume工具，先进入Kafka（自带offset可以均衡的取数据 平衡速率 主要为了实时数仓），再通过Flume工具，进入Hadoop集群。File => Flume => Kafka => Flume => HDFS
  • Mysql业务数据通过增量同步Maxwell工具，进入Kafka，再通过Flume工具，进入Hadoop集群。每日全量DataX工具，进入Hadoop集群。增量同步 mysql => Maxwell => Kafka => Flume =>HDFS，全量同步 mysql => DataX => HDFS。

补充：

  • 采集不仅给离线数仓用，还要给实时数仓用，flink直接对接Kafka就行了。
  • 全量数据同步：表的全部数据。 增量数据同步：表的新增及变化的数据。 与统计需求挂钩。全量数据同步（DataX）不用于实时数据分析。增量数据同步（Maxwell）用于实时数据分析，也用于离线数据分析。

日志数据采集过程：

  1. jar包生成模拟日志数据app.log，
  2. flume路径下创建job的conf配置文件 file_to_kafka.conf，配置source和channel(用不到sink)，通过启动命令自动启动flume采集。推入Kafka topic_log。
  3. 再通过Flume将Kafka的数据同步到HDFS，（其实由于有Kafka，写入hdfs其实是实时的，但实际上离线数仓的取用是每日离线的）。（由于离线数仓采用Hive的分区表按天统计，为了方便所以HDFS目标路径要包含一层日期，Flume工具配置选择KafkaSource、FileChannel、HDFSSink），（KafkaSource订阅Kafka中的topic，增加拦截器：判断json格式数据是否有效，为Event修改header中的时间戳 解决零点漂移问题）（拦截器的jar包放到/flume/lib下）。

业务数据采集过程：

  1. mysql的增量数据通过Maxwell工具（监控mysql的binlog变化的实时流式工具），以json文件格式，推入Kafka topic_db。（采用每日增量同步的表，通常需要首次同步时全量一下，通过Maxwell的bootstrap工具（select *）来进行历史数据的首日全量同步）。Flume工具从Kafka里取数据，存入hdfs里/gmall/db/表名_inc/2022-06-06，（选择KafkaSource、FileChannel、HDFSSink），（也需要一个拦截器，从Event中找表名和日期）。
  2. mysql的全量数据通过DataX工具（基于Select查询的离线、批量同步工具）同步。不进入Kafka。（为了方便所以HDFS目标路径要包含一层日期，故hdfswriter的path参数值应该是动态的）。通过DataX工具，配置mysqlreader、hdfswriter插件的配置json文件，存入hdfs里/gmall/db/表名_full/2022-06-06。

全量同步与增量同步（仅业务mysql数据）

业务数据是状态，日志数据是事件；状态需要一致性同步，事件只需记录发生。

全量同步是指将某张表中的所有数据整体拷贝到目标系统中，适用于对整张表进行统计分析的场景，例如统计网站累计注册用户总数时，只需要一张完整的用户表即可进行简单高效的查询。而增量同步则是指只同步新增或发生变化的数据，适用于对数据变动有明确时间窗口要求的统计需求，例如统计最近一周新增注册用户数。如果仍使用全量同步，需要从庞大的数据集中筛选特定时间段的记录，不仅效率低下，还可能造成系统性能瓶颈。相反，如果使用增量同步，仅记录新增和变化的数据，则可以直接针对小数据集进行分析，效率更高，统计更灵活。
数据采集的方式必须服务于数据仓库建设和后续的统计分析目标，技术选型应以最终分析效果与效率为导向。
