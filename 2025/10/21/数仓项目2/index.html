数仓的设计

ER模型和维度模型

ER模型（实体关系模型，Entity-Relationship Model），用于描述业务系统中的实体、属性及其关系，保证数据一致性与完整性，严格遵循数据库范式（通常至第三范式，3NF）。多表、多外键、多层关系。高频增删改查（OLTP）。通常用于业务数据库、ODS层（操作数据层），保留源系统结构。

维度模型用于支持分析、报表、OLAP查询，强调可理解性与查询性能。面向“分析视角”：度量指标（Fact）如何被不同维度（Dimension）分析。反范式化设计，允许冗余以换取查询性能。适用于数据仓库主题层（DWD/DWS/ADS）。面向分析、反规范化、易理解。数据仓库设计应优先考虑维度建模以满足高效查询需求。
结构形式：

  • 星型模型（Star Schema）：事实表直接关联维度表（最常见）
  • 雪花模型（Snowflake Schema）：维度表再细化（更规范，查询略慢）
  • 星座模型（Fact Constellation）：多个事实表共享公共维度（大型企业常见）
    核心组件：
  • 事实表（Fact Table）：存放度量指标（如销售额、访问量、下单数）
  • 维度表（Dimension Table）：存放分析角度（如时间、商品、地区、用户）

维度模型的核心思想

维度模型将复杂的业务抽象为两个核心概念：事实（Fact）和维度（Dimension）。确定需要统计的行为结果（事实），然后从不同的分析角度（维度）对其进行统计和分析。这种设计理念使得数据仓库的建模更专注于业务的分析需求，从而提供更清晰、高效的数据分析能力。

  • 维度：分析数据的角度
    • 维度是用来描述分析数据的不同视角。如果你想站在性别的角度分析数据，就创建一个“性别表”；想站在省份的角度，就创建“省份表”。
    • 维度表通常包含的是数据的“状态”或“属性”，如性别（男/女）、省份（河北/河南），它们不是行为。
  • 事实：行为的结果，需要统计的数据
    • 事实是需要进行统计和汇总的数据，通常是“行为”所产生的结果。
    • 例如，“登录次数”、“注册用户数”、“订单销量/金额”等都是行为的结果，需要被统计。这些统计结果可以创建一张“事实表”来存储。

为什么设计那么多的分层结构？

值得注意的是，在每一个步骤中我们通常会生成中间结果，并以表的形式保存下来。这些表在 Hive 底层对应的其实是 HDFS 文件。虽然从表面上看，这可能会导致文件数量增多、性能下降，但实际上恰恰相反：这是为了提升性能和复用效率而进行的有意设计。现实中，用户业务需求数量庞大，很多统计与分析场景会复用相同的原始数据或中间结果。若每次都从头计算，势必浪费资源。因此，我们通过“缓存”方式将关键节点的数据以表格形式保存，实现中间结果的复用。其原理类似 Spark 中的缓存（cache）机制，目的就是避免重复读取、重复计算，从而提高整体系统性能。

综上所述，数据仓库的内部结构不仅仅是线性的计算流程，更是一个高度模块化、可复用的计算体系。通过合理的中间数据表设计和缓存策略，不仅能够满足高并发、多需求的业务场景，还能显著提升系统的运行效率和资源利用率。

ODS层（Operational Data Store，操作型数据存储层）

  • ODS 层叫数据源层，本质是“对接层”：

    • 对接业务数据库、日志采集系统；
    • 将来自不同源系统的数据进行融合。
    • 尽管有融合操作，但它被视为最接近原始数据的层。
    • 是为了解决直接使用源系统数据作为数据源的困难。

  • 什么情况“可以变”？

  • 日志数据结构融合：

    • 比如启动日志和浏览日志都是 JSON，但字段结构不一样；
    • 为了统一存储（避免建太多表），可以做异构结构融合，存储在同一张表中（比如用一个大字段装 JSON 或按 superset 建表）。

  • 时间维度汇总需求：

    • 虽然 ODS 层原则是“保留原始”，但出于分区存储、提高查询效率考虑，有时会做按天、小时等时间粒度的汇总。

DWD 层（Data Warehouse Detail，明细数据层）

  • 对原始数据（ ODS层数据）进行加工处理后得到的结构化数据层。类似于Word Count中对原始文本的清洗和格式化。

  • 加工目标：使数据更详细、更准确，为后续的统计分析、数据建模提供高性能、规范化的支持。

  • 存储方式改变：从数据库对接的行式存储（适用于 OLTP）变为列式存储（适用于 OLAP）。

D (Dimension) 层 - 维度层（公共维度层）

  • 存放用于分析数据角度的数据，如性别、品牌、产品分类等。

  • 强调“公共性”，即这些维度可以被多个事实（统计结果）共享和复用，例如性别维度可以用于分析订单销售、登录次数或用户注册数量。

DWS 层（Data Warehouse Summary，统计汇总层）

  • DWS 层是数仓的统计汇总层，主要职责是对经过清洗和加工后的明细数据进行统计分析和汇总处理。

  • 作用核心：求和（总金额等）、计数（订单数量、用户数等）=分组统计（按维度聚合数据）。

  • DWD 和 DWS 层可能存在数据冗余，但这是为了保证数据处理的独立性、复用性和性能优化。空间换时间：牺牲一些存储空间来换取查询统计的高效性。

ADS 层（Application Data Service，数据服务层）

  • ADS 是数据仓库的最顶层，主要承载对统计结果的分析，其本质是：

    • 面向 “应用服务” 的一层；
    • 承载的是 最终呈现给业务方/产品方/客户的分析结果；
    • 属于数据仓库的 “对外输出” 层。

  • ADS 层 不再做基础统计，只是在其基础上进行业务场景分析与展现；

为什么要把分析结果存表？
重复使用：一次分析结果可以反复使用，节省计算成本；
便于对接前端系统（如 BI、报表系统）：提供结构化表，方便查询展示；
服务化输出：将统计分析结果服务化，满足用户系统对外访问；

数据仓库学习的核心重点

学习重点并不是写 SQL 本身，SQL 是“结果”的一部分，真正影响你能否写出高效 SQL 的核心在于：底层数据表的设计（建模）是否合理。数据模型结构设计决定了 SQL 的复杂度和执行效率。

优先掌握建模方法论（如星型模型、雪花模型、宽表模型）。

数仓分层架构

层名称 英文全称 中文含义 说明
ODS层 Operation Data Store 操作数据存储层（原始数据层） 存储经过简单融合和处理的原始数据，不完全是纯原始数据，数据融合操作存在
DWD层 Data Warehouse Detail 详细层（经过加工后的详细数据） 对ODS数据进行加工，符合统计分析需求，数据更准确详细
维度层 Dimension 维度层（公共层，多个业务分析共享同一套维度数据） 存储各种分析角度，如性别、品牌、产品分类，属于公共共享的分析维度
DWS层 Data Warehouse Summary 汇总层 存储汇总数据，如合计、总和等，是报表中的汇总信息
ADS层 Application Data Store 应用层 数据仓库最终统计结果的存放层，提供对外数据服务（API、报表等）

数仓的环境 具体实现

Hive on Spark

  1. Hive 的核心作用：将用户编写的 SQL (HQL) 语句进行解析，然后将其转换为底层的执行程序（如 MapReduce 或 Spark 程序），并提交给计算引擎执行。
  2. 传统引擎 MapReduce (MR)速度较慢，是其主要缺点。现代引擎 Spark 成为了更优的选择。
  3. 流程：Hive 接收 SQL 语句，将其解析并转换为 Spark 程序（RDD 操作），然后将 Spark 程序提交给 Spark 集群执行。

模拟数据生成

概述：
独立性：数据仓库的开发不依赖于真实的数据采集通道，即使采集通道有问题，只要能将数据模拟生成到中间件（HDFS、Kafka、MySQL）中即可。
业务数据：通常有历史数据（在数据仓库上线前就已经存在于业务数据库中）。
用户行为日志：通常没有历史数据，从数据仓库上线之日开始生成。

业务数据同步到 HDFS：
全量表：将 MySQL 中的业务全量表（例如 base_category、base_trademark 等）同步到 HDFS。使用 DataX 进行全量数据同步。检查 HDFS 上 /user/gmall/db 目录下有 17 张全量表的对应数据，确认数据格式（DataX 默认同步为 TSV 格式，字段间由 Tab 键分隔）。
增量表：将 MySQL 中的业务增量表（例如 order_info、payment_info 等）在首日进行全量同步。使用 Maxwell 监听 MySQL Binlog 变化。

ODS层

  1. 数据格式
    日志数据：JSON 格式。
    业务数据：
    全量表：TSV (Tab-Separated Values) 格式。
    增量表：JSON 格式。

  2. 数据汇总
    目的：将 MySQL 中分散的、可能只保留部分历史数据的数据，汇总到数据仓库中，形成完整的数据集。
    考虑因素：MySQL 通常不会存储所有历史数据。数据仓库需要存储海量数据（例如，十年）。

  3. 数据压缩
    目的：减少存储空间，提高资源利用率。
    压缩算法选择Gzip：Gzip 压缩率极高，适合存储海量历史数据。是 Hadoop 默认支持的压缩格式，无需额外配置。

  4. 表命名规范
    目的：从逻辑上区分数据仓库中的不同层次的表。
    命名规则：ODS_表名_全量/增量标识
    ODS：表示该表属于 ODS 层。
    表名：与 MySQL 业务数据库中的表名一致。
    全量/增量标识：_FULL：表示全量表。_INC：表示增量表。

ODS 日志表建表语句

日志表的完整名称为：ODS_LOG_INC，

CREATE EXTERNAL TABLE ods_log_inc (...)，EXTERNAL 关键字：表示创建的是一个外部表。
内部表 vs. 外部表：
内部表：Hive 管理表的数据和元数据。删除内部表时，会同时删除表的元数据和底层 HDFS 上的数据文件。
外部表：Hive 只管理表的元数据，不管理底层 HDFS 上的数据。删除外部表时，只删除元数据，保留底层 HDFS 上的数据文件。

为什么选择外部表？
在学习和开发阶段，我们可能需要频繁地修改表结构（加字段、改配置），然后重新创建表。如果使用内部表，每次重建表都需要重新上传数据，非常麻烦。使用外部表，数据文件保留在 HDFS 上，即使删除并重建表，数据也还在，避免了重复上传数据的操作，提高了开发效率。

PARTITIONED BY (dt STRING)，
目的：提高查询效率。Hive 表的数据量通常非常大，通过将数据按照某个条件（如日期、地域等）划分到不同的 HDFS 路径下，可以减少每次查询时扫描的数据量，从而加快查询速度。
